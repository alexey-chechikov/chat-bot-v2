# ТЗ для Claude: данные ATLAS, TradingView и наших сборщиков — 13.10.2026

## 0. Цель и границы работы

Нужно определить, какие данные и признаки полезны для нашей ручной торговли на 15 минутах, WEEX-сеток и maker-бота на оборот. У оператора уже есть **платная подписка TradingView**. Учти её как имеющийся ресурс, но проверь конкретный тариф, доступные функции, качество данных и допустимые способы использования. Не предполагай, что платная подписка автоматически даёт настоящий биржевой агрессор, полный стакан, неограниченную историю или права на машинный сбор.

Результат должен отвечать: **что уже имеется; что исправить; что можно добавить; какой источник выбрать; каким экспериментом доказать торговую пользу**. Не ограничивайся списком индикаторов или пересказом презентации.

Работа — аудит, офлайн-прототипы и проверяемые рекомендации. Можно подготовить исправления сборщиков и тесты в отдельном коммите. Не менять живые торговые настройки, не размещать/снимать ордера и не подключать новый источник к автоматическим решениям живых ботов в рамках этого задания. Существующие TradingView alerts не менять. Новый внешний сбор/приёмник не разворачивать до проверки разрешений и отдельного решения оператора.

## 3. Аудит наших существующих источников

Прочитай минимум:

- `services/weex_book/recorder.py`;
- `services/weex_api/client.py`;
- `services/deriv_live/loop.py`;
- `collectors/storage.py`, сборщики trades/orderbook/liquidations;
- `research/weex/maker_paper.py`;
- существующие Pine/TradingView интеграции проекта — найди их и проверь реальное назначение.

В исходном срезе GPT установлено:

| Источник | Что записывает код | Ограничение |
|---|---|---|
| WEEX BTC/ETH | `book`: E + цена/объём трёх bid и трёх ask; `trades`: T,E,p,q,m | Подписка depth15, на диск только top-3; нет trade ID, локального receive-time и событий gap/resync |
| Binance BTC/ETH/XRP | aggTrade и depth20@100ms | В нормализованной схеме теряются IDs/sequence/receive-time; заявленная частота не равна измеренной задержке |
| Контекст деривативов | Binance OI/funding/mark/index и некоторые ratios; частично Bybit | Пауза между проходами 300 s; часть source timestamps теряется |
| Ликвидации | Реализованы несколько биржевых адаптеров | Наличие кода не доказывает правильность и полноту потока |
| Исполнения нашей сетки | price, qty, fee, maker, order_id, cum_qty | Journal timestamp — время обнаружения с точностью секунд, не точное биржевое время fill |

Проверь фактическую работу: какие службы запущены, какие файлы действительно растут, покрытие по времени, gaps, задержки, дубли, ошибки нормализации. Отчёт по коду и отчёт о фактической записи разделить. Ключи и содержимое приватных журналов в публичный репозиторий не публиковать.

**Сначала перепроверь конкретные дефекты:**

1. Bybit `allLiquidation` документирует `T,s,S,v,p`. Старый парсер ждёт `updateTime,symbol,side,size,price`; документированный формат даёт пустой символ и нули. `S=Buy` — ликвидирован LONG, а не SHORT. `p` — bankruptcy price, не обычная цена сделки. [Bybit docs](https://bybit-exchange.github.io/docs/v5/websocket/public/all-liquidation).
2. OKX `sz` для деривативов измеряется контрактами; для USD notional нужны `ctVal/ctType`. Старое `sz*bkPx` не универсально. В приложенной иллюстрации при условном `ctVal=0.01` ошибка составляет 100 раз; множитель в примере не является запросом текущей спецификации BTC. Feed OKX не обещает все ликвидации. [Инструменты](https://app.okx.com/docs-v5/en/#public-data-rest-api-get-instruments), [liquidation feed](https://app.okx.com/docs-v5/en/#public-data-websocket-liquidation-orders-channel).
3. Hyperliquid-адаптер ждёт `liquidation` в public trades, но этот флаг не входит в описанный `WsTrade`. Не считать такой канал подтверждённой ликвидационной лентой. [Subscriptions](https://hyperliquid.gitbook.io/hyperliquid-docs/for-developers/api/websocket/subscriptions).
4. WEEX: сохранять IDs, непрерывность стакана и весь доступный depth. Переподключение не должно маскировать потерянные сделки как полную историю. Направление `m` сверить с документированным `isBuyerMaker`, сохранить исходное поле.
5. Для собственного cost accounting проверить signed fees/rebates и отдельные фактические возвраты: `max(delta,0)` не подходит для отрицательной комиссии, если источник её действительно возвращает. Не считать обещанный ребейт полученным.

Подготовь meaningful tests по реальным документированным схемам: массив сообщений, дубли, пропущенные/неизвестные поля, неправильные units и price basis. Неполноту не заменять нулями и «здоровым» status.

## 4. Что именно собирать и нормализовать

Первый контур — BTC/ETH: Binance + Bybit как внешний контекст, **WEEX отдельно как площадка исполнения**. Другие инструменты добавлять после проверки units/качества; GC, XAUUSD CFD, XAUUSDT и PAXG не объединять в один инструмент.

Минимальные таблицы:

| Таблица | Обязательные сведения |
|---|---|
| Trades | venue, instrument/product, trade/aggregate ID, exchange execution/event time, receive UTC + monotonic time, price, native qty/unit, normalized base qty/USD notional, aggressor method, raw side |
| Orderbook | snapshot/delta, sequence IDs, exchange/receive times, session ID, все полученные уровни, признак применимости/пропуска |
| Instrument metadata | contract size, ctVal/ctType где нужны, tick/qty step, base/quote/settlement currency, версия и время получения |
| OI/funding | venue/product, native OI и units, source timestamp, mark/index, funding rate/interval/next time; прогноз и фактический платёж отдельно |
| Liquidations | source timestamp, сторона ликвидированной позиции, units, notional method, bankruptcy/execution price basis, ограничения полноты источника |
| Own execution | order/client/trade ID, exchange fill time, send/ACK/cancel times, qty/VWAP, maker/taker, signed fee и валюта, принадлежность стратегии |

Сырые public сообщения хранить в закрытом исследовательском хранилище с retention и метаданными; публично — код, схемы, synthetic fixtures и агрегированные результаты. Все нормализации версионировать. Синхронизацию часов измерять, единый глобальный порядок между площадками не выдумывать.

WEEX документирует public OI `/capi/v3/market/openInterest`, funding history `/fundingRate`, premiumIndex/mark/index, trades и WS depth. Наличие документации — не доказательство доступности с нашего IP: сделать отдельный public smoke check и сохранить дату/схему. Секреты для этого не требуются. [Market API](https://www.weex.com/api-doc/catalog/core-trading-futures/api/rest-api/market-api), [Public WS](https://www.weex.com/api-doc/catalog/core-trading-futures/api/ws-streams/public).

Не суммировать объёмы в contracts, BTC и USDT без преобразования. Не смешивать spot и perpetual по умолчанию. OI в долларах может расти только из-за роста цены; изменение количества контрактов показывать отдельно. Агрегированная цена не заменяет исполнимую WEEX bid/ask для оценки сделки.

## 5. TradingView: инвентаризация платной подписки и способов получения

Заполни матрицу **available / approximate / unavailable / permission_pending** для фактического аккаунта. Если доступа к тарифу нет, оставь это неизвестным и продолжай биржевую часть; не останавливай всё исследование ради вопроса оператору.

Проверить:

- точный тариф, доступные symbols/таймфреймы, фактическую глубину истории;
- exchange-qualified тикер, spot/perpetual/dated contract, units объёма, real-time/delayed feed;
- OHLCV, VWAP/Anchored VWAP, ATR/volatility, relative volume;
- Volume Profile: POC, VAH/VAL, HVN/LVN; окно, bins, алгоритм и момент доступности уровня;
- Volume Delta/CVD; source lower-TF, reset/anchor и timezone;
- Footprint total/buy/sell/delta, POC/VA/imbalances; способ доступа к числовым значениям;
- OI/другие данные, только где они действительно доступны для нужного инструмента;
- CSV, Pine plots, native alerts и ограничения каждого способа.

**Подтверждённые ограничения, которые учитывать:**

1. Standard Volume Delta/CVD классифицируют объём по движению цены младших свечей. Назвать метод `price_direction_estimate`, не `exchange_aggressor_delta`. [Volume Delta](https://www.tradingview.com/support/solutions/43000725057-volume-delta/), [CVD](https://www.tradingview.com/support/solutions/43000725058-cumulative-volume-delta/).
2. Footprint использует внутрисвечное направление цены; глубина истории меняет детализацию. Документация допускает repainting, включая уже закрытые бары при переходе realtime→history. Фиксировать размер price rows и проверять значения после reload/через сутки. [Footprint guide](https://www.tradingview.com/support/solutions/43000726164-volume-footprint-charts-a-complete-guide/).
3. `request.footprint()` уже есть в Pine v6; по текущим docs нужен Premium/Ultimate. Допускается одна уникальная footprint request на script, включая дополнительные `request.security*` контексты; предусмотрено `na`. Проверить фактическую компиляцию/данные. Не писать устаревшее «footprint нельзя получить в Pine». [Pine docs](https://www.tradingview.com/pine-script-docs/concepts/other-timeframes-and-data/#requestfootprint), [limits](https://www.tradingview.com/pine-script-docs/writing/limitations/).
4. CSV содержит загруженную историю и plots; таблица/рисунок индикатора не гарантируют экспорт его внутренних данных. Проверить реальные columns/timestamps/NA и покрытие. [CSV export](https://www.tradingview.com/support/solutions/43000537255-how-to-export-chart-data/), [Pine export](https://www.tradingview.com/pine-script-docs/faq/indicators/#is-it-possible-to-export-indicator-data-to-a-file).
5. Webhook — событие alert, не поток каждой сделки. Есть ограничения частоты и доставки; alert хранит копию кода/inputs. На tick-based charts server-side alerts недоступны. Рассмотреть техническую возможность только для допустимого применения, не приравнивая её к лицензии на сбор. [Alerts](https://www.tradingview.com/pine-script-docs/concepts/alerts/), [webhooks](https://www.tradingview.com/support/solutions/43000529348-how-to-configure-webhook-alerts/), [rate limit](https://www.tradingview.com/support/solutions/43000690939-alert-was-triggered-too-often-and-stopped/), [tick intervals](https://www.tradingview.com/support/solutions/43000709225-what-are-tick-based-intervals/).
6. Платный тариф не включает автоматически все биржевые realtime entitlements. DOM зависит от брокерского подключения; это не универсальный экспорт L2. [Дополнительные данные](https://www.tradingview.com/support/solutions/43000471705-how-to-purchase-additional-market-data/), [L2](https://www.tradingview.com/support/solutions/43000480004-how-do-i-get-level-2-data/).
7. Официального пользовательского API выгрузки market-data/indicator values TradingView не предоставляет. Datafeed API для charting library требует собственный источник данных. [API FAQ](https://www.tradingview.com/support/solutions/43000474413-i-need-access-to-your-api-in-order-to-get-data-or-indicator-values/), [Datafeed API](https://www.tradingview.com/charting-library-docs/latest/connecting_data/datafeed-api/).

**Допустимый scope:** текущие [Terms §3](https://www.tradingview.com/policies/) ограничивают данные, charts/alerts/webhooks display-only и запрещают перечисленные non-display применения. [Правила автоматического сбора](https://www.tradingview.com/support/solutions/43000674726-why-is-my-account-banned-due-to-suspicious-activity/) отдельно ограничивают scraping/automated extraction. Платную подписку не считать разрешением на такой сбор. Для TV downstream потребовать проверку конкретных разрешений/отдельного соглашения с TV и поставщиком. Не проектировать обход внутренних WebSocket, rate limits или защит. Ручные встроенные функции и визуальный анализ оценивать в пределах разрешённого scope; наличие CSV-функции не гарантирует любой дальнейший машинный use. Для автоматических решений нашего бота базовый путь — документированные биржевые/лицензированные feeds.

Если TV-внешний эксперимент permission_pending, выполнить воспроизводимый аналог метода TV на собственном разрешённом биржевом сырье и визуальную сверку доступных данных; не выдавать это за проверку реального TV-export. Исследовательскую работу по другим источникам продолжать.

## 6. Проверка гипотезы «TradingView не хуже прямого источника»

Разделить **точность данных** и **полезность для стратегии**. При доступном разрешённом наборе сравнить один и тот же instrument/venue/product, UTC-интервалы `[open,close)`, одинаковые units и resets. Основной TF — 15m; 1m/5m как диагностика. Сравнивать WEEX с Binance можно как cross-venue контекст, но не как тест точности одного feed.

Получить три ряда:

1. `delta_raw_aggressor`: по собственной сохранённой биржевой ленте с native aggressor.
2. `delta_lower_tf_direction`: по официальному методу TV, рассчитанная из того же собственного потока/младших баров.
3. `delta_tv_export`: фактически доступные и разрешённые числовые значения TV; если отсутствуют — не выдумывать.

Это отделит ошибку метода от различий источника. Сначала OHLCV parity/пропуски; затем bias, MAE, p95 абсолютной ошибки, `sum(abs(D_tv-D_raw))/sum(V_raw)`, согласование знака. Для последнего основная зона исключения — `abs(D_raw)/V_raw < 0.05`; чувствительность 0.02/0.10 показать отдельно, не выбирать красивый порог. При нулевом объёме метрика NA. CVD сравнивать с одним reset, не по абсолютным значениям разных anchors.

Footprint/профили сравнить при одинаковой фиксированной price grid: объём по rows, POC, VAH/VAL, imbalance agreement. Сохранить доступный закрытый вид и последующее историческое состояние, посчитать долю изменившихся признаков/сигналов. Bar-close не объявлять гарантией отсутствия исторического пересчёта.

Не задавать произвольную высокую корреляцию как достаточный допуск. Критерии пригодности выводить из ошибок downstream signals и результата на отложенном периоде. При short history/нет native tape/нет прав дать честный статус «не проверено», а не «равноценный источник».

## 7. Производные признаки — прозрачные, с версией

На собственном разрешённом сырье подготовить минимальный набор:

- total/buy/sell volume, delta и нормированная delta, CVD с заданным reset;
- распределение объёма по цене, POC/VAH/VAL и механический алгоритм HVN/LVN;
- relative volume по сопоставимому времени суток, используя только прошлые данные;
- признак price/delta disagreement: знаки delta и изменения цены; формальный порог, доступность только в момент фиксации;
- spread в bp, доступная глубина по обеим сторонам в фиксированных bp-зонах, L2 imbalance;
- OI change в native contracts и в USD, funding/basis отдельно по площадкам;
- markout собственных fills 1/5/30/60 s, задержки и полный cash cost.

Не называть их точной копией ATLAS. Не заявлять, что L2 раскрывает точную FIFO-очередь, личность участника, spoofing или намерение. Уменьшение агрегированного уровня неоднозначно; моделировать неопределённость и проверять реальные исполнения.

## 8. Три применения и ворота проверки

### A. Maker на оборот — первый приоритет

Проверить, уменьшает ли фильтр сильного встречного потока/ухудшения стакана стоимость оборота, а не просто сокращает количество сделок. Зафиксировать один базовый maker-алгоритм, inventory limit, время удержания и исполнение; сравнить без фильтра, с фильтром и со случайным сопоставимым пропуском входов.

Главные метрики: cash cost на $1 млн **суммарного фактически исполненного** оборота, оборот/час, inventory/max holding, markout и просадка. Комиссии/валюты/фандинг/полученные rebates отдельно. Price PnL уже включает цены исполнения; не вычитать markout второй раз. Не переносить прежние $91–106/M как подтверждённый baseline: сначала исправить maker_paper очередь, expired quotes и финальный выход по mid.

### B. Ручной интрадей 15m

Использовать механический baseline из ТЗ по золоту либо уже замороженный crypto baseline. Сравнить цена → плюс VWAP → плюс native delta → плюс объёмная зона. Отдельно проверить аналог с TV-estimated delta при доступном scope. Все экстремумы/зоны должны быть известны до входа; подтверждённые бары, реальные costs, одинаковый risk budget. Выдать ясную карточку сигнала: контекст, вход, отмена, стоп, выход, размер от риска, качество/источник данных.

### C. Защита сетки

Проверить фильтр **новых входов**, когда spread/depth/поток ухудшаются. Сопровождение owned lots/TP/неизвестных заявок сохраняется. Сравнить ту же сетку без фильтра, с фильтром и exposure-matched placebo. Показывать просадку, итоговый net, funding, уменьшение оборота и упущенную прибыль. Не считать автоматическое улучшение от уменьшения времени в рынке доказательством информативности фильтра.

Для всех трёх: freeze protocol до результата, хронологический holdout, контроль затрат/риска, доверительные интервалы с блоками по дням/неделям. Не отбирать только удачные инструменты, RR и периоды. Не требовать произвольные 90 холостых дней: достаточность оценивать по покрытию режимов, числу независимых наблюдений и неопределённости. Малое число fills проверяет механику, не доказывает прибыль.

## 9. Артефакты и критерии готовности

Сохранить:

1. Матрицу `source → raw fields → method/units → coverage/quality → permitted use → application → status`.
2. Аудит каждого текущего сборщика и meaningful tests; какие ошибки подтверждены на актуальном HEAD.
3. Схемы данных, metadata/versioning, источники и хэши доступных наборов; никакой подмены missing нулями.
4. Проверенный офлайн-прототип расчёта признаков/сравнения и один стандартный запуск. Pine-индикатор для визуальной работы можно подготовить отдельно; фактическую компиляцию не заявлять без проверки.
5. Результаты трёх применений либо чёткие причины, почему конкретная часть ещё не проверена. Старую сумму/скрин не выдавать за новый эксперимент.
6. Приоритетный backlog: P0 качество/units/time → P1 собственные fills и costs → P2 delta/профили → P3 допуск в стратегию. Оценить хранение/ресурсы по замеру, не по необоснованной линейной экстраполяции.

Отчёт: `docs/ATLAS_TRADINGVIEW_DATA_RESEARCH_RESULTS_2026-10-13.md` в той же ветке. Код — в `research/atlas_data/` либо согласованной существующей структуре. Для каждого пункта статус **«готово и проверено» / «приближённо» / «нет данных» / «требуется разрешение» / «отвергнуто»** и следующая конкретная задача.

Итог для оператора: какие данные использовать сегодня для ручного анализа; какой источник подходит автоматическому боту; что добавляет измеримую пользу после costs; что не добавляет. Само наличие платного TV, красивой дельты или публичного API положительного ожидания не доказывает.
