# Начинаем статистику карты ликвидаций CoinGlass — 15.10.2026

**Цель:** отвечать по накопленным сопоставимым случаям, какую зону цена чаще достигает первой и что происходит после неё. Результат должен иметь число наблюдений, горизонт и неопределённость. Одна яркая полоса не даёт готовую вероятность или торговый сигнал.

**Что уже сделано GPT:** создан отдельный неизменяемый SQLite-журнал; пользовательский скрин зарегистрирован локально как reference; реализованы проверка снимков, загрузка закрытых1m цен, разметка будущих исходов и описательная сводка. Есть raw CoinGlass collector для одного явного API-запроса. **52 офлайн-теста проходят.** Production-код/боты/конфиги не менялись, реальные CoinGlass API-запросы не выполнялись, регулярный процесс не запущен.

**Что пока отсутствует:** точная ссылка/настройки пользовательской карты и подтверждённый доступ к её источнику; проверенный numeric adapter реального ответа; подключённый будущий price feed; накопленные допустимые наблюдения; CI/контроли/калиброванный прогноз. На старте: **1 reference, 0 допустимых наблюдений, 0 оценок рынка**. Скрин не имеет видимых symbol/model/venue/range/scale и подтверждённого времени доступности. Имя файла не считается временем прогноза; вчерашние уровни не аннотируются задним числом после просмотра движения.

## 1. Сначала правильно назвать источник

На изображении CoinGlass liquidation heatmap: оценочная концентрация возможных ликвидаций. Это не фактический стакан и не подтверждённый денежный объём уже ликвидированных позиций. Яркость не вероятность. [CoinGlass explanation](https://www.coinglass.com/prime), [отдельные API datasets](https://docs.coinglass.com/reference/endpoint-overview).

В существующем коде источники смешиваются:

- `core/exchange_liquidity_engine.py` группирует цены **уже прошедших** liquidation events и выставляет `heatmap_ready`. Это не восстановленная CoinGlass-карта.
- `services/analysis_service.py` предпочитает exchange context; наличие OI может дать `ok=True` и не допустить CoinGlass fallback.
- `core/coinglass_client.py` запрашивает карту, но оставляет только две nearest цены/силы. Нет полного immutable снимка/модели/времени получения; текущий рекурсивный parser не подтверждён fixture настоящей матрицы.
- `core/liquidation_character.py` выдаёт эвристические «probability». Искусственный пример дал continuation78% и exhaustion30%. Это не калиброванные частоты; для конкурирующих исходов сумма108% не распределение вероятностей.
- В публичном репозитории **уже есть raw архив фактических ликвидаций** с recv/exchange time, units/price basis. Эту выполненную часть прежнего ТЗ сохраняем. Локальный collector старее публичного; deployment здесь не проверен.

Проверенный источник этого аудита: `e1fe76a50c226872de6831edaa23c2ef3f30f466`; релевантные core/collector файлы не изменились в `dce860dc67c227d31be5b217847f8467b1190e68`. Полный read-only разбор и пять synthetic контрпримеров — в starter-архиве. **Не показывать нынешние scores как вероятности по статистике карты.** До обучения новый модуль всегда выдаёт `forecast_status=not_calibrated`.

## 2. Протокол сбора для Claude

1. По ссылке пользователя зафиксировать symbol/contract, provider, pair или aggregated scope, выбранную модель, range, настройки threshold/scale/resolution, биржи/coverage. BTC по обрезанному изображению не подтверждён. Один immutable `settings_id` и явный `selection_rule_id` до просмотра будущей цены. При изменении параметров — новая серия.
2. Получать снимки каждые **15 минут** с одинаковыми настройками. Сохранять каждую попытку, в том числе error/stale/missed slot; никаких выборочных снимков только красивых карт. Этот cadence — ТЗ, сейчас scheduler не подключён.
3. Сохранять полный raw ответ/изображение локально до извлечения признаков, SHA256, UTC send/receive/capture/annotation-lock, request params без ключей. Новая карта не исправляет старую. Историческая ось текущей матрицы не доказывает, что её значения были известны тогда.
4. Автоматический источник — официальный разрешённый API при фактическом доступе; ключ только в env на машине исполнения. Prime не подтверждает Professional/Enterprise API. [Heatmap endpoint](https://docs.coinglass.com/reference/liquidation-heatmap) документирует `range`, но не исторический `as_of/start_time/end_time`. Для начала не требуется покупать подписку: возможны согласованные ручные снимки, но они остаются отдельной серией.
5. На реальном sample response проверить `y_axis`, `[x_index,y_index,intensity]`, price candles с seconds timestamps, последний столбец, sparse/missing semantics, revision behavior и единицы. **Starter сохраняет raw и валидирует shape, но не предполагает, что отсутствующая sparse ячейка равна нулю или intensity=USD.** Shape-valid не означает готовый normalized profile.
6. Цена для исходов — один явный native market source того же контракта, закрытые UTC1m с exact grid; mark/trade basis отличать. Записывать symbol/source/receipt/coverage и версии исправлений. Корректировка старой свечи — новая dataset version, не перезапись существующего факта. Неполная/дублированная свеча не становится нулевой доходностью.

Сырые provider данные, пользовательский скрин, ключи и runtime DB остаются локально. В публичную ветку — код, протокол, synthetic fixtures и разрешённые собственные агрегаты; права получения/распространения проверять по [условиям CoinGlass](https://www.coinglass.com/terms). Не заменять доступ обходом скрытых endpoints.

## 3. Что записываем из карты

Первый исполнимый режим starter — **две заранее аннотированные зоны**: nearest upper/lower, их границы и capture spot. Метод ручного выбора должен быть постоянным и зарегистрированным; snapshot выбирается до исхода. Пока metadata не подтверждены, сохранение только reference. Код блокирует старше2min, future timestamps, неправильные границы, неизвестную модель и лишние секретные поля.

Затем добавить validated numeric adapter на реально полученный профиль. До его первого расчёта отдельно заморозить правило объединения bins/отбора зон. Нельзя взять только полосы, которые потом отработали.

Нужные будущие признаки:

- расстояния upper/lower в процентах и в **известном до решения** ATR;
- ширина и сила ближайших зон; strongest и nearest — разные признаки;
- суммарная концентрация сверху/снизу в одинаковых окнах0,5%/1%/2%, нормализация только внутри сопоставимой шкалы;
- сколько зоне лет, её усиление/ослабление, смещение/исчезновение между ранее сохранёнными снимками;
- прошедшие ликвидации, OI, funding, trend/volatility как отдельные источники с временем доступности.

Эти дополнительные признаки **не реализованы/не обучены starter**. Полосы первоначального snapshot заморожены навсегда для его исхода. Новый снимок фиксирует новое состояние; исчезнувшую полосу не удалять из старого теста.

## 4. Точные исходы уже работающего prototype

Время решения — первая UTC minute open **строго после** effective freeze. При ручной аннотации freeze=max(получение, окончание аннотации/запись), поэтому нельзя задним числом назвать прогнозом время старого изображения. От freeze до регистрации возраст данных≤2min.

Окна — **15/60/240 минут**. На каждом окне:

| Исход | Правило |
|---|---|
| `UPPER_FIRST` | high закрытой1m впервые достигает near boundary верхней зоны раньше нижней |
| `LOWER_FIRST` | low впервые достигает near boundary нижней зоны раньше верхней |
| `AMBIGUOUS` | обе границы достигнуты в одной первой1m; очередность неизвестна |
| `NO_HIT` | всё окно полное, ни одна граница не достигнута |
| `PENDING` | ещё не закончилось время окна; будущие свечи не используются |
| `CENSORED` | окно закончилось, но необходимые минуты отсутствуют; не приравнивать к no-hit |

Достижение/проход порога — описание цены, а не гарантированный fill/точное касание. Gap через полосу отмечается отдельно. Если до последующего пропуска уже известен first hit, он хранится отдельно, но полная запись не объявляется complete.

После одностороннего первого достижения смотреть **первый подтверждённый1m close**: close минуты достижения и59 следующих закрытых минут. Для upper: rejection=close≤near−0,15% capture spot; continuation=close≥far+0,15% capture spot. Для lower — зеркально. Нет подтверждения на полном окне → unresolved; дырки→censored, срок не закончился→pending. Это начальный фиксированный threshold, не найденный по лучшей доходности. ATR-реакция из methodological note — отдельный будущий вариант, **не текущий код**.

Дополнительно считаются будущие close return/MFE/MAE; выходные `*_fraction` — доли (`0.001=0.1%`), не торговый PnL. После первого hit полный high/low его минуты не считается известным порядком событий; post-hit excursion берётся по следующим60 полным минутам, поэтому созревает на минуту позже реакции. Касание само по себе не называется разворотом или закреплением.

## 5. Статистика без завышения уверенности

Основная выборка: **00:00/06:00/12:00/18:00 UTC**, первый допустимый effective freeze после слота в пределах2min. Выбор происходит **до** проверки исхода/полноты. Пропущенный/неполный слот нельзя заменить следующим красивым complete case. Шестичасовой шаг не даёт перекрывать4h first-hit плюс до60min реакции; серийная зависимость рынка всё равно остаётся.

Дополнительные15m снимки — вторичный ряд: он перекрывается, его n не число независимых движений. Три горизонта — зависимые labels одной записи. Серии разделяются по provider/model/range/scope/exchanges/settings/selection/price source и по two-sided/one-sided наличию зон.

Starter `summary` даёт counts всех статусов и **наблюдаемые исторические fractions**. В denominator остаются no-hit и ambiguous; незавершённые/повреждённые отдельно. **CI и прогнозная модель пока не реализованы.** Нельзя читать 7/10 как готовую вероятность70% следующего движения.

Следующая задача Claude после сбора:

1. day/week block CI с числом реальных дней/кластеров и coverage;
2. baseline price/distance/trend/volatility на тех же snapshot/targets;
3. общий исход фиксированных±1ATR targets для price-only и price+map, чтобы геометрия зон не подменила пользу интенсивности;
4. time split, например60d train +30d запечатанного forward test, scaler/thresholds только train; модель/главный горизонт выбирать до test;
5. основная метрика улучшение OOS Brier score, paired week/day CI и calibration; дополнительное log loss. При отсутствии добавки к price-only сохранить отказ, не перебирать новые пороги на том же test.

Только после этого возможен ответ: «при таких условиях upper-first чаще baseline, N случаев/дней, CI, срок; альтернативы lower/no-hit». Размер confidence не выводится из цвета. Доходность вход/SL/TP после costs — отдельная задача, даже хороший прогноз карты ещё не стратегия.

## 6. Передача Claude и воспроизведение

Соседний **[HEATMAP_STATS_STARTER_2026-10-15.zip](https://github.com/alexey-chechikov/chat-bot-v2/blob/alexey/mac-2026-05-29/docs/HEATMAP_STATS_STARTER_2026-10-15.zip)** содержит `prototype/journal.py`, `labels.py`, `stats.py`, `collect_coinglass.py`, тесты, official/methodology/reuse notes, manifest. В нём нет пользовательского скрина, DB, vendor raw, реальных keys или приватного торгового state.

Только stdlib Python3.12. Из `prototype/`:

```text
python -m unittest -q test_journal test_labels test_collect_coinglass test_stats
python journal.py status
python journal.py reference <local-image-path>
python journal.py snapshot <fresh-operator-verified-normalized.json>
python journal.py bars <closed-1m.csv> --source <explicit-source-version> --symbol <symbol>
python journal.py evaluate
python journal.py summary
```

`--db <local-path>` задаётся **перед** подкомандой. Без аргумента DB находится в `local/journal.sqlite` относительно родительской папки prototype. `reference` не создаёт eligible forecast. Функция `sample()` в `prototype/test_journal.py` формирует только **synthetic** fixture, её нельзя добавлять в реальную статистику.

Collector command — в `prototype/COLLECTOR_README.md`: один запрос по явно указанным параметрам и envkey, никакого scheduler/бота на import. Не запускать примерный model2/Binance как настройки пользователя. При подключении Claude сначала подтверждает доступ и validates real response fixture, затем добавляет разрешённое расписание/health/coverage и future price feed. Действующие торговые боты этот модуль не читают.
