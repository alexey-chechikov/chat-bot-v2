## 1. Что это и зачем

Оператор торгует сетками на GinArea (облачный сервис ботов; OKX). Здесь — своя сетка на бирже
WEEX (USDT-фьючерсы, бессрочные), повторяющая правила GinArea Default grid, но **исполнение
лимитками, выставленными заранее** (GinArea бьёт по рынку). Цель оператора — **оборот**: биржа
возвращает комиссию (приветственный бонус, затем кэшбэк по объёму до 77.6%), поэтому важны
число кругов и полный итог с мешком.

Счёт: хедж-режим (отдельные позиции LONG и SHORT по символу), кросс-маржа, плечо 100, депозит
— несколько тысяч USDT (точная сумма — в пакете, переданном напрямую). На том же символе оператор торгует руками — у биржи это ОДНА позиция стороны,
сетка различает свои ордера по префиксу `b7g` в clientOrderId и чужие никогда не трогает.

## 2. Цикл

- Раз в `poll_sec` = 10 с (плюс время прохода) — проход `tick()` по каждой сетке.
- Ошибка одной сетки не мешает другим; при ошибке пауза 60 с, предупреждение в Telegram не
  чаще раза в 30 мин.
- Запросов: 2 чтения на проход (bookTicker + openOrders вес 2) ≈ 12 запросов / ~18 веса в минуту;
  статус ордера (вес 2), сделки ордера (вес 5), история ордеров (вес 10) — только по событиям.
  Ордеров ≈ 140/сутки. Лимиты WEEX в публичных материалах расходятся (исправлено 10.10 по разбору:
  «~1%» не подтверждено замером заголовков).
- Время подписи берётся с сервера биржи (±30 с), пересинхронизация раз в час.

## 3. Один проход `tick()` (на сторону LONG / SHORT отдельно)

Обозначения: d = +1 для лонга, −1 для шорта; `lots` — открытые лоты стороны
(вход, объём, цена тейка, ордер тейка); `entry` — текущий входной ордер; `ref` — опорная цена.

1. **Снимок биржи.** Стакан (bid/ask), открытые ордера с префиксом `b7g` этого символа.
   **Сироты** (свои ордера, о которых учёт не знает): вход — снять, исполненное записать лотом;
   тейк — снять (10.10).
0. **Потерянный ответ (10.10).** Перед каждой постановкой на диск пишется намерение `pending`
   (clientOrderId, вид, цена, ключ лота). Ответ получен → `pending` снимается. Исключение (сеть) →
   `pending` остаётся; следующий проход ищет ордер по clientOrderId в открытых, затем в истории
   ордеров (`/capi/v3/order/history`); найден → привязывается (вход/тейк лота), не найден 120 с →
   считается не дошедшим. Пока не выяснено — на этой стороне новых ордеров нет.
2. **Входной ордер.** executedQty у биржи накопительный: пишется только ПРИРОСТ против уже
   записанного (`filled`, `filled_val`, `fee_done` в ордере) — цена прироста из прироста стоимости,
   комиссия — прирост комиссии ордера; повтор того же снимка = 0. Прирост пишется и пока ордер
   ещё висит (исполненная часть сразу получает тейк). Частично исполненный вход не переставляется —
   остаток добирается на том же уровне. Ордер забываем ТОЛЬКО в конечном статусе; при снятии —
   если отмена ещё не прошла (CANCELING), ждём следующего прохода.
3. **Тейки.**
   - Тейк на бирже не того объёма, что лот (биржа урезала reduceOnly) → снять; исполненная до
     снятия часть записывается; затем новый тейк.
   - Тейка нет среди открытых → статус: живой → ждём; конечный → исполненное (целиком или
     частично) = прибыль d·объём·(цена − вход), лот уменьшается на исполненное; остаток → новый тейк.
   - У лота нет тейка → ставим reduceOnly POST_ONLY лимитку объёмом ЭТОГО лота.
   - Тейк отклонён → сверка с позицией биржи: если лотов в учёте больше позиции стороны,
     лишние лоты без тейка (новые первыми) снимаются, их результат пишется в закрытое по текущей
     цене как оценка внешнего закрытия + сообщение оператору (10.10: раньше исчезали бесплатно).
4. **Опорная цена (правило GinArea).**
   - Есть лоты → `ref` = крайний ОТКРЫТЫЙ лот: у лонга нижний, у шорта верхний.
     Следующий вход = ref × (1 − d·шаг). После тейка уровень заполняется снова.
   - Лотов нет → `ref` тянется за ценой: у лонга за максимумом, у шорта за минимумом
     (вход ждёт отката на шаг от экстремума).
5. **Можно ли добавлять:** стоп/выключено; лотов < `max_lots_per_side`;
   max(себестоимость, текущая стоимость лотов) + новый объём·цена ≤ `max_notional_usd`
   (10.10: раньше только текущая стоимость — на падении докупали сверх потолка);
   стресс-бюджет (выключен). Холостой режим при оставшемся живом учёте: живой проход с
   enabled=false снимает живые входы, тейки остаются (10.10).
6. **Входной ордер.** Если стоит и цена/объём отличаются < 0.05% — оставить. Иначе снять
   (если успел исполниться — записать лот и больше ничего в этом проходе), поставить новый.
7. **Сохранение** состояния после каждого действия (перезапуск не плодит дубли).

**Выставление ордера (`_place`).** POST_ONLY: покупка не дороже bid, продажа не дешевле ask
(если уровень уже пройден — ставим по лучшей цене своей стороны стакана, исполняется как мейкер);
округление к шагу цены вверх для продажи, вниз для покупки. Любая ошибка биржи по одному
ордеру не ломает проход (лог `place_failed`).

## 4. Учёт

- По сторонам: закрыто (сумма прибыли тейков), комиссии (по сделкам ордеров), мешок
  (Σ d·объём·(mid − вход)), оборот (объём × цена входов и выходов).
- Итог сетки = закрыто − комиссии + мешок. Фандинг не учитывается (ВОПРОС, см. §8).
- Журнал каждого исполнения: `state/weex_grid_journal.jsonl`.
- Проверка 09.10: деньги по сделкам биржи (только ордера `b7g`, остаток по текущей цене)
  совпали с учётом бота до $0.0000 по обеим сторонам (скрипт `research/weex/pnl_reconcile.py`).

## 6. Инциденты 09.10 и исправления (все с тестами)

4. Входные ордера висели старым объёмом после смены размера → переставляются.
5. Опорная цена от последнего ИСПОЛНЕННОГО входа (а не от крайнего открытого) → после тейков

## 7. Отличия от GinArea (известные)

| GinArea Default | Здесь | Влияние |
|---|---|---|
| Рыночные ордера при пересечении уровня | Лимитки заранее (мейкер) | Дешевле; уровень, пройденный за 10 с, добирается одним ордером по текущей цене, а не «пачкой» |
| Тейк: триггер на цели → стоп-профит на Мин.стоп ниже, трейлинг Макс.стоп, объединение в Out Stop | Лимитка ровно на цели | Прибыль круга = цель (у GinArea цель − Мин.стоп + трейлинг) |
| Инстоп (вход после разворота) | Нет | У ботов оператора инстоп = 0 |
| Множитель шага/размера | Нет | Не используются |
| Выход по средней (obap) | Нет (тейк по каждому лоту) | У BTC-сетки оператора — тейк по ордерам |
| Односторонний режим (позиция нетто) | Хедж (стороны отдельно) | Экономически то же; фандинг платится с обеих сторон |
| Старт после полного закрытия | Вход на шаг от экстремума после отката | ВОПРОС: у GinArea, вероятно, сразу по рынку — не проверено |

## 8. Риски и открытые вопросы — прошу оценить

1. **Нет стопа.** Защита только числом ордеров и потолком $4 000 на сторону. В тренде мешок
   растёт до потолка и стоит. Потолок считается по ТЕКУЩЕЙ стоимости — при падении цены
   разрешает докупать (стоимость лотов падает), т.е. себестоимость может превысить $4 000.
   ВОПРОС: считать потолок по себестоимости?
2. **Общая позиция с ручными сделками.** Если оператор закроет «всю позицию» в приложении —
   закроются и лоты сетки; сетка это поймёт только когда тейк не встанет (сверка с позицией).
   Если ручная позиция больше — сверка консервативна и призрака не увидит.
3. **Фандинг не в учёте.** Хедж-режим платит/получает по обеим сторонам.
4. **Комиссия.** Факт 0.016% мейкер на сторону; сейчас биржа возвращает каждую комиссию
   отдельным начислением (бонус). Бэктесты считают комиссию без возврата.
5. **Частичные исполнения.** Лот = исполненный объём; хвост ордера снимается при перестановке.
6. **Задержка 10 с.** На резком движении часть уровней пропускается (GinArea сложила бы их
   в один ордер).
7. **Эдж.** По нашим замерам прибыль сетки = оборот × маржа(цель), а итог решает мешок на конце
   окна. Это НЕ прогноз и не эдж в цене — доход от возвратов цены, плата — хвост.
