# Win → Mac: drift-монитор альт-гридов + апдейт сканера (2026-06-11)

**Запрос оператора:** всесторонний анализ ДО входа + бот сам ведёт анализ ПОСЛЕ входа; при раскореляции
(инструмент выпадает из пилы в дрейф) — эскалация: **сигнал → расширить step/target ×2 → если упорно → закрыть.**
Посоветуйся со мной по реализации. Ниже — что я сделал (Win) + что прошу собрать/решить у тебя (Mac).

## A. Сканер (ДО входа) — `tools/_alt_grid_scan.py`, 3 правки (из разбора WLD 10.06)

1. **Жёсткий отсев пампов:** `pump = |t1|>12% или |t7|>35%` → score=0, флаг 🚫памп. WLD уехал −8.4% за день
   (откат пампа = дрейф = враг грида). Не пускать грид на свежепампленое.
2. **Ранжирование к ПИЛЕ, не к размаху:** было `score ~ rng24` (брал максимальный размах = максимальный дрейф-риск).
   Стало пик размаха ~4% + множитель `(1−ER)` (низкий ER = пила). Берём чоп, не клюшку.
3. **Охват от ВОЛАТИЛЬНОСТИ символа** (был флэт 12% для всех): `span = clamp(12×√vr, 8, 24)%`.
   Проверено: vr=1→12%, vr=2→17%, vr=3.5→22%. Волатильнее = шире коридор (нормальный ход внутри) +
   меньше поза (тот же $-риск при более широком стопе%). SL −175 остаётся жёстким бэкстопом.

## B. Drift-монитор (ПОСЛЕ входа) — `tools/_grid_drift_monitor.py`, ГОТОВ + валидирован

Потребляет твой поток снимков (формат `snapshots.csv`: ts, position, profit, current_profit). Функция
`assess(df, tsl)` → стадия 0..3 + действие. Сигналы (из робастных полей трекера):
- `bag_pct = (current_profit−profit)/tsl` — доля жёсткого SL, съеденная **мешком** (стоп бьёт мешок, не общий — см. ниже).
- `pos_pin` — пригвождена ли позиция к одному краю (пила оссциллирует позу, дрейф пригвождает).
- `bag_accel` — ускорение углубления мешка за 20 мин (раскореляция = мешок ускоряется).

**Лестница (идея оператора, формализована):**
| Stage | условие | действие |
|---|---|---|
| 0 healthy | мешок<40% SL или поза не пригвождена | ничего |
| 1 WARN | мешок≥40% SL + поза пригвождена | сигнал «односторонний дрейф, следить» |
| 2 ADAPT | мешок≥55% + пригвождена + углубляется | **step/target ×2** (коридор + крупнее доход на отскоке) |
| 3 EXIT | мешок≥75% + пригвождена + углубляется | **закрыть бота** (не ждать −175 на дне) |

## C. Валидация на живых данных 10.06 (3 бота) — ЧЕСТНО

```
SOL (рейнджер, +34): max Stage 1 (блипы 15:46/15:54 при мешке 46% SL) -> НЕ закрыт -> +34 цел ✓
XRP (рейнджер, +16): Stage 0 весь день ✓
WLD (дрейфер, −99): Stage1 с 11:19 -> Stage2(расширить) 13:38 и 16:04 -> Stage3(закрыть) 16:14 в total −78
```
**Что монитор даёт (доказано):** чисто РАЗДЕЛЯЕТ рейнджеров (≤Stage1, не трогаем) и дрейфера (→Stage3).
Никаких ложных закрытий на победителях. WLD закрыли бы в **−78 vs факт −99** (экономия ~$21, ~20% убытка).

**Что НЕ даёт (стена причинности):** ранней магии нет. До 16:00 WLD выглядел здоровым (realized рос
+22→+47, мешок осциллировал ~−55). Подтверждение дрейфа приходит на 82% SL — бóльшая часть урона уже есть.
Stage2 (расширить) пару раз сработал на ноге, что потом восстановилась (13:38) — но расширение дёшево/обратимо.
**Монитор = реактивный (на ПОДТВЕРЖДённый дрейф), не предсказательный.** Это потолок, честно.

## D. КРИТИЧНО для твоего симулятора: стоп = по МЕШКУ, не по общему

Проверено на WLD: стоп `tsl=−175` сработал, когда **мешок** (`current_profit−profit`) пробил −181, хотя
**общий** (`current_profit`) был лишь −110. **Подсказка в UI GinArea («общий текущий профит ≤ значения») для
Dynamic-Auto ВРЁТ.** В симе стоп-условие: `current_profit − profit ≤ tsl`.
