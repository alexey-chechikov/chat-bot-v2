## Семь идей в формате раздела 8

### 1. Логический вход отдельно от фрагментов его исполнения

**Идея:** Считать слоты по логическим входам, сохраняя отдельный учёт fills и немедленную защиту исполненной части.

**Механизм:** Сейчас каждый прирост partial-entry становится новым lot/TP. API-фрагментация случайно меняет разрешённую экономическую загрузку. Parent order/уровень занимает один экономический слот; child fills сохраняют цены, fees и exit allocation. Объединение допустимо только при сохранении правил выхода; нельзя ждать полного entry ради одного TP. Нового плательщика нет: устраняется несогласованность реализации.

**Отличие от опровергнутого:** Не урезание/расширение числа ордеров ради прибыли и не выход всей стороны по средней. Смысл лимита не должен зависеть от того, одним или двенадцатью fills биржа исполнила ту же заявку.

**Тест на наших данных:** Replay одинаковых исполнений целиком и фрагментами; равны qty/cost/fees, исходные целевые exit cashflows и допуск следующего entry. После этого реальный lifecycle replay с тем же риском; функциональные инварианты не требуют signal placebo. Экономику дополнительных входов проверять отдельно по воротам 1–5.

**Ожидаемый эффект:** Воспроизведено при **одинаковых .005 BTC / $500**: 50 fills по .0001 занимают 50 слотов и блокируют entry; четыре полных .0012 и один .0002 занимают пять слотов и entry разрешён. Cap в обоих случаях $4000. Равенство количества проверено точно. Частота такого дробления live неизвестна; прибыли не обещаю.

**Критерий отказа:** Слияние меняет exit targets, теряет fill/fee либо оставляет часть без TP. Также нельзя автоматически повышать риск до $4000 и считать это улучшением.

**Реализация:** Parent-entry ID, child-ledger, отдельные economic-slot и actual-open-order лимиты; TP aggregation только по совместимым ценам и с сохранённым распределением. Средняя сложность.

**Главный риск:** Устранение случайного ограничения увеличивает возможный inventory. Денежный и общий стресс-лимит должны работать независимо от числа фрагментов.

### 2. Фиксировать пройденный тейк по достижимой чистой цене

**Идея:** Отдельная политика для выхода, когда исполнимая bid/ask уже прошла первоначальный TP.

**Механизм:** `_place` всегда POST_ONLY и переносит пересекающий стакан TP к текущему ask/bid. Затем котировка может остаться дальше исходной цели. Проверить два варианта: passive repricing с сохранением минимальной net-цели и ограниченный reduceOnly IOC по цене, которая после реального taker fee сохраняет требуемую чистую прибыль. Источник результата — доступное обратное движение; ускорение выхода покупается дополнительной комиссией.

**Отличие от опровергнутого:** Не «лимитка вместо маркета улучшает сигнал». Входы прежние; меняется только обработка уже доступного выхода. Maker-only здесь явный экономический tradeoff.

**Тест на наших данных:** WEEX timestamps fills/ack, bid/ask/depth, maker/taker tariffs, cancel outcomes. Сравнить исходный maker-only, passive repricing и один фиксированный hybrid. Те же входы и inventory; сначала event replay, затем новый период после фиксации. Ворота 1–5 по всему PnL, пропущенные fills и fees включены.

**Ожидаемый эффект:** Синтетика: entry100, TP100.3, poll100.99/101.01 ставит TP101.01; возврат bid100.49 не закрывает, затем mid99 даёт **−$1.016**. Немедленный выход по100.99 с **условным**, не проверенным taker .05% дал бы **+$0.923505**. Чтобы сохранить net исходного maker-TP, при этих тарифах нужен bid≥**100.334119**, а не просто bid≥100.3.

**Критерий отказа:** Дополнительные fees/slippage больше сохранённого PnL либо свежий полный результат не лучше maker-only. Синтетический контрпример не даёт частоты события.

**Реализация:** Exit policy с фактическими комиссиями, net-price threshold, лимитом slippage, terminal cancel/fill tracking. В клиенте уже есть неиспользуемый `futures_commission`. IOC поддержан [официальным V3 API](https://www.weex.com/api-doc/catalog/core-trading-futures/api/rest-api/transaction-api); это не гарантия полного исполнения. Средняя сложность.

**Главный риск:** Гонка отмены и нового выхода, shallow book, taker fee, частичный IOC. Допускать только после исправления учёта из предыдущего обзора.

### 3. Проверить устойчивость уровней повторного входа

**Идея:** Сравнить нынешний ref от крайнего открытого лота с постоянными идентификаторами ценовых уровней.

**Механизм:** После TP крайнего лота ref перескакивает к следующему, а свободный cap может немедленно использоваться рядом со стаканом. Альтернатива сохраняет ticket исходного уровня для refill, с явными правилами прекращения старой серии. Это меняет путь набора inventory и восстановления уровней; не создаёт новый ценовой сигнал.

**Отличие от опровергнутого:** Не множитель шага 1.05 и не ATR-расширение. Шаг/цель остаются прежними; меняется идентичность уровня после закрытия. Текущий вариант соответствует описанному GinArea-правилу, поэтому это абляция политики, **не обнаруженный баг**.

**Тест на наших данных:** Одинаковые исходные минуты/fills, exact live cap/50, непрерывный state. Один альтернативный алгоритм, без одновременных новых exits/sizing. Сравнить baseline, persistent tickets и постоянное уменьшение q с сопоставимой загрузкой. Старый/средний/новый блок, ворота 1–5; не выбирать удачный anchor по final.

**Ожидаемый эффект:** В исходном Grid: лоты100+99, cap200 — ref99 и desired98.802; после TP99.3 ref100, desired99.8 и новый POST_ONLY entry **99.39**. Изменение политики может сократить churn или, наоборот, пропустить лучшие круги. Исторический прирост не установлен.

**Критерий отказа:** Меньше turnover без улучшения полного PnL/хвоста относительно inventory-matched контроля; на новом пути правило хуже baseline.

**Реализация:** Исследовательский level_id/refill-state; исходный GinArea baseline сохранить. Средняя сложность.

**Главный риск:** Постоянные уровни устаревают при тренде, оставляют простаивающий капитал; выбор их начала становится ещё одним параметром подгонки.

### 4. Общий риск до входа и после возможного TP

**Идея:** Единый резерв счёта, включая состояние, когда компенсирующая сторона закрылась первой.

**Механизм:** Разрешать новые entry по общей книге, pending/remaining и сценариям порядка exits. Gross и net ограничивать отдельно; прибыльный TP не запрещать, риск будущего состояния резервировать при наборе. Это сохранение заработанного дохода за счёт ограничения накопления, не дополнительный источник дохода.

**Отличие от опровергнутого:** Не открытие LONG+SHORT пары, не прогноз стороны и не новый трендовый hedge. Конкретное упущение: TP уже существующей выигравшей ноги уменьшает gross, но может увеличить абсолютный net. Старый общий stress-budget здесь уточняется переходами TP и общим reservation.

**Тест на наших данных:** Общий капитал/все позиции, исторические mark/fills, сценарии adverse shock до/после TP, все ещё исполнимые entry. Контроль — постоянно меньший размер с сопоставимыми net/gross и непрерывные случайные entry-паузы той же загрузки. Ворота 1–5, отдельно headroom/CVaR. Функциональный запрет двойного расходования бюджета проверяется без placebo.

**Ожидаемый эффект:** Прямой `may_add`: equity1000, бюджет250; три сетки разрешают stress210 каждая, совместный условный 10% shock **630**. Другой сценарий: LONG/SHORT .048 BTC по80000, shortTP79832 приносит8.064 и оставляет netLONG .048; при72000 итог **−377.78** с fees, возврат до longTP требует **+11.34%**. Это арифметика, не прогноз следующего рынка.

**Критерий отказа:** Резерв обходится pending/partial; экономический вариант не лучше меньшего постоянного размера при том же риске.

**Реализация:** Один account-admission и durable reservations перед POST, обновление после fills. Средняя/высокая сложность.

**Главный риск:** Net-ноль не стирает уже накопленный paired loss. LONG40@100+SHORT40@90 дают −400 при80/95/110; одним net-cap gross ограничение заменять нельзя.

### 5. Цена времени удержания и funding перед новым набором

**Идея:** Сначала измерить возраст/дистанцию выхода всех лотов, затем проверить отдельный admission по carry и старому inventory.

**Механизм:** Использовать существующий lot timestamp `t`, но учитывать и незакрытые лоты. Измерять notional-hours, saturation, required rebound и settlement cashflows; проверить, когда предполагаемая маржа нового круга уступает консервативной стоимости удержания. Старые TP сохраняются; принудительного age-exit нет. Funding является денежным расходом/доходом, его платит противоположная сторона.

**Отличие от опровергнутого:** Не funding-детектор флэта, не «закрыть на стадии дрейфа», не выход по средней и не TP по sigma. Это уточнение ранее предложенного carry-бюджета с честной длительностью и стоимостью занятого лимита.

**Тест на наших данных:** Entry/exit/funding trace по всем cohorts, right-censored duration. Старый блок для оценки, следующий для фиксации, новый для решения. Раздельно тестировать age-admission и carry-admission, сравнить с постоянным меньшим net и matched pauses. Реальные WEEX ставки/mark и account income, ворота 1–5. [V3 market API](https://www.weex.com/api-doc/catalog/core-trading-futures/api/rest-api/market-api) предоставляет funding history, mark/index и период начисления; Binance служит только proxy.

**Ожидаемый эффект:** На152д baseline closed median26мин против oldest still-open96.95д и distance32.62%. Круг LONG$100,target.21% после двух maker fees даёт **$0.1779664**. Условные +.01% funding каждые8ч съедают его примерно за **5.93д** netLONG. Но на данном Binance replay funding **+13.06**, поэтому именно этот расход не объясняет основной минус.

**Критерий отказа:** Сэкономленный carry меньше потерянного ценового результата; длительность некалибрована на новом блоке; admission не лучше простого меньшего размера.

**Реализация:** Сначала trace/карточка и полный funding ledger; затем два раздельных shadow-эксперимента. Средняя сложность.

**Главный риск:** Только закрытые TP дают survivorship bias; возраст не сигнал направления. Автоматическое расширение TP ради funding может ещё увеличить duration.

### 6. Проверить разные выходные бюджеты сторон

**Идея:** Раздельная экономика LONG/SHORT и фиксированный эксперимент с разными целями после измерения holding/carry.

**Механизм:** Одинаковая `target_pct` не означает одинаковую стоимость цикла. Проверить денежную цену выхода каждой стороны при прежних входах, общем капитале и риске. Нового плательщика нет; возможна более подходящая частота фиксации. Это диагностика, а не подтверждённая новая alpha.

**Отличие от опровергнутого:** Подкрутка целей сама по себе уже не считается новым механизмом. Здесь недостающее измерение — раздельная стоимость удержания; выбирать прибыльную сторону постфактум недопустимо. Доход от выбора лучшей ячейки на той же истории не доказательство.

**Тест на наших данных:** При одном common step сравнить общую цель, заранее фиксированные LONG .3/SHORT1 и зеркальный вариант. Тот же капитал/50слотов, side equity синхронно, fresh/carry, fees/funding/фактический rebate. Разработка/валидация и новый final; ворота 1–5, контроль той же загрузки. Для XAU исходные минутки в проверенном пакете отсутствуют, независимого replay нет.

### 7. Качество котировки и очередь вместо лишнего индикатора

**Идея:** Собирать данные об исполнимой цене, свежести, fills и потерях очереди; сначала проверить правила котирования в shadow.

**Механизм:** `book()` сейчас возвращает только bid/ask, отбрасывая доступные bidQty/askQty/time; depth/mark/index не используются. Измерять, сколько реального edge забирают задержки, переналив/неналив и cancel-requote. Политика отмен/обновлений может сохранять очередь либо избегать заведомо плохого stale quote; доход за ликвидность оплачивается противоположным потоком, но неблагоприятный отбор способен его съесть.

**Отличие от опровергнутого:** Это уточнение уже предложенного execution/markout исследования, не OI/funding режимный выключатель и не гарантированный эдж от лимиток. Markout служит диагностикой, не заменяет full PnL с потерянными прибыльными fills.

**Тест на наших данных:** Синхронные WEEX quotes/depth, источник fair value того же типа контракта, order IDs, place/cancel ack, fills и timestamps. Для XAU отдельно контрактный индекс, schedule и качество источника. Baseline против одного фиксированного freshness/requote правила и того же числа отмен со сдвигами в сопоставимых блоках; новый final, ворота 1–5. Минутные Binance свечи этого теста не заменяют.

**Ожидаемый эффект:** Не измерен. В опубликованном XAU.75/.3 запас полного результата270.76 на turnover606900.83 равен всего **4.46bps оборота**: дополнительные средние1bps расходов съедают **60.69**. Это чувствительность, не измеренное проскальзывание. Для BTC даже нулевые комиссии не убирают отрицательный inventory-результат исходной10м конфигурации.

**Критерий отказа:** Улучшился markout, но full PnL хуже; преимущество исчезает при delay/queue либо не отличается от простого снижения активности.

**Реализация:** Read-only collector и shadow metrics; затем event-driven обслуживание fills, budget запросов/ордеров по exchangeInfo, отдельная очередь защитных exits. API-доступность не гарантирует успешное исполнение или преимущество. Высокая сложность.

**Главный риск:** Ошибочный fair value, утрата queue priority, асинхронные partial fills и cancel. Увеличивать частоту poll без измерений/API-бюджета нельзя считать улучшением.

## Отдельно: что улучшить в методологии

- **Новые входы против старого мешка:** в одной и той же cutoff-позиции сравнить A=старые TP+новые entry и B=только старые TP. Пометить old/new лоты; PnL старого inventory второй части считать от cut mark, не исходного entry. Разница A−B проверяет предельный вклад новых входов. Fresh/carry разных anchors этого не делают.
- **Каждое изменение отдельно:** исправленный учёт, pooling, hybrid exit и новый admission нельзя включить вместе и затем приписать результат одному из них.
- **Базовый ресурс одинаков:** общий equity, маржа, max50, cap и резерв живых/неизвестных заявок. Новые тесты на152д используют50; опубликованная развёртка использовала10000. Это разные модели.
- **Состояние не обнулять бесплатно:** restart/fresh anchor не удаляет реальный старый inventory; закрытие оплачивается. Нужны carry и fresh как разные вопросы плюс matched-state контроль.
- **Открытые лоты обязательны:** closed median/PF/TP count исключают главный хвост. Наш replay даёт6179TP и всё равно−563.71.
- **Новый final обязателен:** все данные/таблицы выше уже просмотрены. Они позволяют отвергнуть заявления, найти механику и выбрать один эксперимент, но не подтверждают независимое положительное ожидание.
- **Rebate денежный и фактический:** XAU1/1 без возврата лучше.75/.3 (285.72против270.76), при77.6% возврате порядок обратный (305.18против346.12). Порог смены выбора≈20.76% cash-return. Нельзя оптимизировать стратегию под неподтверждённый бонус.

## P1 — дефекты, которые могут изменить позицию или оставить её без учёта

### 1. Ошибка конфига XAU/ETH переключает обработчик на BTC

[engine.py:81](https://github.com/alexey-chechikov/chat-bot-v2/blob/65eae0295bd99c91cedec8ca0c8f05edf4a4d44b/services/weex_grid/engine.py#L81), [loop.py:112](https://github.com/alexey-chechikov/chat-bot-v2/blob/65eae0295bd99c91cedec8ca0c8f05edf4a4d44b/services/weex_grid/loop.py#L112).

При malformed/unreadable config `load_config` возвращает глобальный DEFAULT с `symbol=BTCUSDT`, теряя template XAU/ETH. Это не просто выключение: `_live_leftovers` запускает живой проход с этим BTC config и старым state другой сетки.

**Воспроизведено:** неполный JSON XAU + прежний лот 0.023 XAU → отменена действующая собственная BTC entry и отправлен **reduceOnly SELL BTCUSDT объёмом 0.023** от золотого лота. Биржевая судьба этой ошибочной заявки не утверждается: fake её принимает, реальная биржа может отказать/урезать/исполнить в зависимости от BTC-позиции. Само обращение к неверному символу доказано.

**Исправление:** ошибка конфига — отдельное состояние отказа, сохранение идентичности символа/template, запрет торговых решений до восстановления. Проверять согласованность grid name/config/state/ордеров. Атомарное сохранение config снижает вероятность обрыва, но не заменяет безопасную обработку ошибки.

### 2. Orphan-вход забывается до terminal; возможны второй вход и повторный fill

[engine.py:297](https://github.com/alexey-chechikov/chat-bot-v2/blob/65eae0295bd99c91cedec8ca0c8f05edf4a4d44b/services/weex_grid/engine.py#L297), [engine.py:323](https://github.com/alexey-chechikov/chat-bot-v2/blob/65eae0295bd99c91cedec8ca0c8f05edf4a4d44b/services/weex_grid/engine.py#L323).

`_cancel_and_take` не сохраняет неизвестную заявку как tracked и не требует terminal. `_orphans` удаляет её из open snapshot независимо от успеха отмены. Каждый следующий poll создаёт новый dict без cumulative cursor.

**Воспроизведено три проявления:**

- Отмена отказана, старый вход NEW 0.0012; тот же tick ставит второй 0.0012 → **0.0024 BTC входных заявок**, учёт знает только одну.
- CANCELING и неизменный cumulative fill 0.0004; два poll → **реально 0.0004, виртуально 0.0008**.
- Поздний FILLED после CANCELING исчезает из openOrders → **реально 0.0012, виртуально 0, TP нет**, даже при enabled=false.

**Исправление:** durable recovery record до отмены, постоянные fill/fee cursors и резерв remaining; terminal reconciliation до освобождения записи/разрешения нового входа.

### 3. Повреждённый state запускает пустой бот и снимает имеющийся TP

[engine.py:124](https://github.com/alexey-chechikov/chat-bot-v2/blob/65eae0295bd99c91cedec8ca0c8f05edf4a4d44b/services/weex_grid/engine.py#L124), [engine.py:137](https://github.com/alexey-chechikov/chat-bot-v2/blob/65eae0295bd99c91cedec8ca0c8f05edf4a4d44b/services/weex_grid/engine.py#L137).

Прямая `write_text` не атомарна; ошибка чтения существовавшего state приравнивается к первому запуску. Защитные ордера становятся orphan, а исполненный вход уже отсутствует в openOrders.

**Воспроизведено:** после имитации truncated JSON restart отменяет TP старой реальной позиции 0.0012, оставляет virtual qty=0 и ставит новый вход 0.0012. Это дефект обработки повреждения; не утверждение, что такой сбой уже случился в вашем журнале.

**Исправление:** atomic temp-write/flush/fsync/replace; повреждённый/потерянный существующий state требует восстановления по intent/fills до новых входов и отмен защит. Не подменять его пустой стратегией.

### 4. Partial external close удаляет весь лот вместо дефицита

[engine.py:461](https://github.com/alexey-chechikov/chat-bot-v2/blob/65eae0295bd99c91cedec8ca0c8f05edf4a4d44b/services/weex_grid/engine.py#L461).

`_reconcile_side` удаляет выбранные лоты целиком, пока held>exchange size.

**Воспроизведено:** лот 0.0012, после внешнего сокращения осталось 0.0008, replacement TP один раз отклонён → **на бирже 0.0008, в учёте 0, TP нет**. Оценочный выход записан на все 0.0012 вместо исчезнувших 0.0004. Обычный POST_ONLY reject не доказывает отсутствие всей позиции.

**Исправление:** согласовывать именно дефицит количества, сохранять остаток и его защиту. При несогласованных/запаздывающих снимках оставлять явное расхождение и блокировать добавление, а не стирать подтверждённый лот.

### 5. TTL 120с и первые 100 history orders не доказывают, что POST не дошёл

[engine.py:265](https://github.com/alexey-chechikov/chat-bot-v2/blob/65eae0295bd99c91cedec8ca0c8f05edf4a4d44b/services/weex_grid/engine.py#L265), [client.py:115](https://github.com/alexey-chechikov/chat-bot-v2/blob/65eae0295bd99c91cedec8ca0c8f05edf4a4d44b/services/weex_api/client.py#L115).

Потенциальное суммарное количество 0.0024. Частота такого события в реальном счёте не установлена; после долгого простоя/активной ручной истории условие вполне отличается от baseline-теста.

**Исправление:** полнота поиска в пределах времени intent, direct client-ID lookup при поддержке, проверка fills. TTL запускает уведомление/карантин, не доказывает отсутствие side effect.

### 6. Потерянный TP mapping скрывает исполненный выход

[engine.py:323](https://github.com/alexey-chechikov/chat-bot-v2/blob/65eae0295bd99c91cedec8ca0c8f05edf4a4d44b/services/weex_grid/engine.py#L323).

Orphan reduceOnly только отменяется, его fills не читаются и не распределяются по лотам.

**Воспроизведено:** TP от 0.0012 исполнил 0.0004, state потерял TP reference. Код пропускает **+$0.06972**, сохраняет virtual 0.0012 вместо actual 0.0008. Урезанный replacement успешно принимается, поэтому reconciliation не вызывается; следующий tick снова отменяет и переставляет его из-за несовпадения qty.

**Исправление:** восстановить TP allocation и выходные fills до replacement; неизвестный владелец — явное расхождение, не бесплатная отмена.

### 7. Старый partial-entry резервируется по новому размеру config

[engine.py:203](https://github.com/alexey-chechikov/chat-bot-v2/blob/65eae0295bd99c91cedec8ca0c8f05edf4a4d44b/services/weex_grid/engine.py#L203), [engine.py:553](https://github.com/alexey-chechikov/chat-bot-v2/blob/65eae0295bd99c91cedec8ca0c8f05edf4a4d44b/services/weex_grid/engine.py#L553).

После уменьшения order size may_add считает новый `cfg.order_qty`, но старый частично исполненный ордер остаётся с исходным remaining.

**Воспроизведено:** origQty=0.0012 по $80,000, исполнено 0.0002; новый qty=0.0001 и cap=$50. Ордер оставлен, хотя его полное исполнение даёт **$96 себестоимости при лимите $50**.

- **Journal append и state save не одна транзакция.** Сбой между ними повторяет fill в journal после restart: journal qty 0.0024/turnover $239.52 при корректном state qty 0.0012/$119.76. В journal нет orderId/tradeId для надёжной дедупликации. Это дефект журнала, не удвоение Grid.st PnL в данной трассе. Нужны event IDs и согласованный commit/replay.
- **`/start` lost update.** [loop.py:241](https://github.com/alexey-chechikov/chat-bot-v2/blob/65eae0295bd99c91cedec8ca0c8f05edf4a4d44b/services/weex_grid/loop.py#L241): старый tick сохраняет halted=true после команды, которая уже подтвердила enabled/снятие halt. Следующий tick также остановлен. Нужен один владелец state/общая синхронизация. Stop/dry в гонке могут поставить ещё один вход после текущего текста подтверждения; допускается асинхронная семантика, но ответ должен различать pending и applied.
- **Включённый stress разрешает риск при equity=0/−1 или ошибке balance.** [engine.py:219](https://github.com/alexey-chechikov/chat-bot-v2/blob/65eae0295bd99c91cedec8ca0c8f05edf4a4d44b/services/weex_grid/engine.py#L219). Неизвестный баланс должен блокировать добавление. `loop.sigma24` жёстко BTCUSDT для всех сеток; при включении stress ETH/XAU используется не их волатильность. Эти замечания относятся к включаемой защите, не к причине опубликованного BTC-теста со stress=0.
- **Цена меняется после cap-check.** [engine.py:233](https://github.com/alexey-chechikov/chat-bot-v2/blob/65eae0295bd99c91cedec8ca0c8f05edf4a4d44b/services/weex_grid/engine.py#L233): после ask-clamp/rounding пример notional $4000.46412 вместо разрешённых $3994.08 при cap=$4000. Считать окончательные price/qty до допуска.

Защитный крайний случай отдельно: `success=true` без orderId уже стирает pending; наличие именно такой формы реального WEEX acknowledgement не установлено, поэтому не используется как основной довод о безопасности.

Его exit=0 не означает, что все деньги совпали. С реальным полным журналом и account statement этот пункт можно проверить; по публичному коду он не подтверждается.

## Уже признанные ограничения

Shared manual/grid ownership не изолирован; close/reopen между polls может быть невидим. Полный ledger, точные внешние закрытия, funding и доступный денежный rebate не реализованы. Maker queue/markout не собраны. Исправления частичных состояний не создают торговый эдж. Отсутствие стопа и portfolio liquidation/risk model — отдельная политика, которую потолок по cost/value не заменяет.

## Приоритет следующего изменения

Сначала безопасная идентичность config/state, атомарное сохранение и durable отслеживание всех pending/orphan/cancel/TP fills. Затем reconciliation только точного дефицита и резерв фактического remaining. После этого независимый fee/funding ledger и один владелец команд/state. Для параметров стратегии повторить exact live limits, исправить cut/DD и добавить реальные venue traces. Увеличение оборота не исправляет перечисленные ошибки.

```python
"""Offline diagnostics of the pinned fixed-quantity grid on Binance futures proxy data.

This is sensitivity analysis, not a WEEX execution backtest or a new out-of-sample result.
The original engine and snapshot are not modified. No exchange client is instantiated.
"""
import csv
import hashlib
import importlib.util
import json
from dataclasses import dataclass, field
from datetime import datetime, timezone
from pathlib import Path

import numpy as np

ROOT = Path(__file__).resolve().parent
SNAP = ROOT.parent / "weex_code_review_20261010" / "snapshot"
DATA = ROOT.parent / "expectancy_20261006" / "public_data"


@dataclass
class Side:
    d: int
    lots: list = field(default_factory=list)
    ref: float | None = None
    realized: float = 0.0
    fees: float = 0.0
    turnover: float = 0.0
    entries: int = 0
    tps: int = 0
    cost: float = 0.0
    qty: float = 0.0


def run(data, funding, mode="colour", one_entry_per_minute=False):
    ts, op, hi, lo, cl = data
    states = {"LONG": Side(1), "SHORT": Side(-1)}
    fee, q, step, target, cap, slots = 0.00016, 0.0012, 0.002, 0.0021, 4000.0, 50
    closed_ages, blocked_minutes = [], {"LONG": 0, "SHORT": 0}
    cash_funding = 0.0
    peak_vertex = peak_close = peak_hour = 0.0
    dd_vertex = dd_close = dd_hour = 0.0
    gross_hours = net_abs_hours = paired_hours = 0.0
    max_gross = max_net = 0.0
    monthly = {}
    max_lots = {"LONG": 0, "SHORT": 0}

    def equity(px):
        return sum(s.realized - s.fees + s.d * (s.qty * px - s.cost) for s in states.values())

    for i, t0 in enumerate(ts):
        t0 = int(t0)
        if t0 in funding:
            rate, mark = funding[t0]
            cash_funding -= (states["LONG"].qty - states["SHORT"].qty) * mark * rate
        if mode == "low_first" or (mode == "colour" and cl[i] >= op[i]):
            prices = (op[i], lo[i], hi[i], cl[i])
        else:
            prices = (op[i], hi[i], lo[i], cl[i])
        added = set()
        for px in prices:
            for name, s in states.items():
                keep = []
                for entry, qty, tp, birth in s.lots:
                    if (s.d > 0 and px >= tp) or (s.d < 0 and px <= tp):
                        s.realized += s.d * qty * (tp - entry)
                        s.fees += fee * qty * tp
                        s.turnover += qty * tp
                        s.tps += 1
                        s.qty -= qty
                        s.cost -= qty * entry
                        closed_ages.append((t0 - birth) / 3600)
                    else:
                        keep.append((entry, qty, tp, birth))
                s.lots = keep
                if s.lots:
                    s.ref = min(x[0] for x in s.lots) if s.d > 0 else max(x[0] for x in s.lots)
                elif s.ref is None:
                    s.ref = px
                else:
                    s.ref = max(s.ref, px) if s.d > 0 else min(s.ref, px)
                level = s.ref * (1 - s.d * step)
                touched = px <= level if s.d > 0 else px >= level
                allowed = max(s.cost, s.qty * px) + q * level <= cap and len(s.lots) < slots
                if touched and allowed and (not one_entry_per_minute or name not in added):
                    s.lots.append((level, q, level * (1 + s.d * target), t0))
                    s.qty += q
                    s.cost += q * level
                    s.fees += fee * q * level
                    s.turnover += q * level
                    s.entries += 1
                    added.add(name)
                max_lots[name] = max(max_lots[name], len(s.lots))
            ev = equity(px)
            peak_vertex = max(peak_vertex, ev)
            dd_vertex = min(dd_vertex, ev - peak_vertex)
        px = cl[i]
        ev = equity(px)
        peak_close = max(peak_close, ev)
        dd_close = min(dd_close, ev - peak_close)
        if i % 60 == 0 or i == len(ts) - 1:
            peak_hour = max(peak_hour, ev)
            dd_hour = min(dd_hour, ev - peak_hour)
        gross = (states["LONG"].qty + states["SHORT"].qty) * px
        net = abs(states["LONG"].qty - states["SHORT"].qty) * px
        gross_hours += gross / 60
        net_abs_hours += net / 60
        paired_hours += (gross - net) / 60
        max_gross = max(max_gross, gross)
        max_net = max(max_net, net)
        for name, s in states.items():
            level = s.ref * (1 - s.d * step)
            if max(s.cost, s.qty * px) + q * level > cap or len(s.lots) >= slots:
                blocked_minutes[name] += 1
        month = datetime.fromtimestamp(t0, timezone.utc).strftime("%Y-%m")
        monthly[month] = ev
    px = cl[-1]
    rows = []
    for name, s in states.items():
        for entry, qty, tp, birth in s.lots:
            rows.append({"side": name, "entry": entry, "qty": qty, "tp": tp,
                         "age_hours_right_censored": (int(ts[-1]) - birth) / 3600,
                         "distance_to_tp_pct": (tp / px - 1) * 100 if s.d > 0 else (1 - tp / px) * 100,
                         "unrealized": s.d * qty * (px - entry)})
    age_stats = {str(p): float(np.percentile(closed_ages, p)) for p in (50, 90, 99)} if closed_ages else {}
    return {"mode": mode, "one_entry_per_minute": one_entry_per_minute,
            "total_ex_funding": equity(px), "realized_gross": sum(s.realized for s in states.values()),
            "fees": sum(s.fees for s in states.values()), "turnover": sum(s.turnover for s in states.values()),
```
