# Конечная выгрузка публичного WEEX replay — запрос 18.10.2026

Цель: перейти от двух прежних фрагментов5/12мин к проверке механики пассивного maker на полных, заранее выбранных календарных отрезках. Это запрос существующей записи, не запуск нового сборщика и не доступ GPT к Mac. Экспорт делает оператор с уже разрешённым доступом. Публичный рынок отдельно от счёта/учёта роботов.

## Сначала inventory, затем фиксированный интервал

В ответе указаны одновременно «с14.10», «6дней» и дата18.10. Это ещё не подтверждённые шесть полных суток. Нужен небольшой `inventory.json` по всем реально доступным BTCUSDT/ETHUSDT файлам: UTC first/last event/recv, bytes/SHA256/row_count, схемы, сессии, gap/resync/disconnect и непрерывные валидные spans. Не заполнять пропущенные дни и не выбирать участок по PnL/движению цены.

Предварительно фиксируем **BTCUSDT и ETHUSDT, 16.10.2026 00:00:00–18.10.2026 00:00:00 UTC**: 16октября только техническая калибровка/проверка pipeline, 17октября закрытая временная валидация с уже закреплёнными правилами. Обе монеты сохраняются, исходная maker-ветка включала ETH; результаты монет не объединять для выбора победителя. Не называть17октября untouched OOS, если этот отрезок уже анализировали. Если coverage не позволяет — сначала вернуть inventory/причину, не подменять на удачный шестичасовой участок. При необходимости следующий хронологический полный день закрепляется новым RUN_PLAN до PnL.

Нужен полный предыдущий book snapshot до начала и все следующие сообщения, минимум30мин предыстории и30мин после конца. Если последнее валидное snapshot раньше30мин, включить его и всю цепь deltas до начала. Post-tail нужен для последних заявок с15мин TTL и markout; его нельзя использовать для новых заявок вне основного окна. Если нет18октября00:30UTC, хвост/такие исходы пометить missing. Дневные файлы могут пересекать эти границы: можно передать целые затронутые файлы с manifest вместо опасной фильтрации по одному timestamp.

## Какие файлы нужны без потери структуры

Схема проверена чтением [recorder.py, 1d0da80](https://github.com/alexey-chechikov/chat-bot-v2/blob/1d0da80863226acda8fdf57d07eee087fc08ef2c/services/weex_book/recorder.py). Наличие кода не доказывает coverage архива.

| Файл v2 | Ожидаемые исходные поля | Требование |
|---|---|---|
| `<SYM>_<UTCday>_depth.csv` | `kind,U,u,E,recv_ms,session,applied,b,a` | Все строки snapshot/delta, включая applied=0; b/a исходные JSON без округления, вся записанная глубина15, не top3 |
| `<SYM>_<UTCday>_trades2.csv` | `t,T,E,recv_ms,session,p,q,m_raw` | Все исходные ID/времена/цены/размеры/m_raw, без ресемплинга и превращения в свечи |
| `<SYM>_<UTCday>_events.csv` | `recv_ms,session,event,detail` | connect/snapshot/gap/resync/disconnect и все остальные события; не отфильтровывать плохие периоды |

Legacy `_book.csv` с top3 и `_trades.csv` без recv/session можно приложить как диагностику, но они не заменяют v2. Приватные ордера, API-ответы аккаунта, ключи, env, balances и state/config торговых ботов в пакет не входят.

Формат: исходные UTF-8 CSV, JSON-строки полей сохранены; один ZIP/tar.gz либо части с SHA256 всего архива и каждого файла. `manifest.json`: точная версия recorder/commit, источник endpoint/channel, реальные времена создания/экспорта, timestamp units/semantics, clock synchronization/известная погрешность, native quantity/contract multiplier/price unit, действовавшие tick/step/minqty/minnotional с датой и источником, row counts, UTC min/max каждого времени, session IDs, duplicates/conflicts/out-of-order, валидные spans/причины gaps. Не выдумывать недостающую metadata, unknown остаётся unknown. Опубликованные публичные файлы должны совпадать с хешами экспортёра.

Если сырой публичный WS-архив тоже уже существует, полезны исходные message/batch boundaries и подключения. Не создавать его задним числом. В данном CSV разные trades одной пачки имеют одинаковые E/recv/session, но исходного batch ID/порядка транспорта может не быть. Из этих строк нельзя изобрести точное exchange-vs-client событие или порядок одновременно пришедших сообщений.

## Проверка до оценки стратегии

1. Проверить hashes/schema/единицы и последовательность recorder: `U == previous u`, snapshot после gap/reconnect, семантику applied; не чинить invalid-gap свечным forward-fill. Trade ID дедуплицировать только по документированному контракту, конфликт не стирать.
2. Разделить биржевое время T/E и recv_ms, сессии и границы UTC-файлов. Фактические часы пользователя не считать exchange latency. `m_raw` в текущем recorder — buyer-is-maker, true означает агрессор-продавец; подтвердить договор публичного источника/историческую версию, не переносить правило другой биржи.
3. Точная очередь отдельных заявок по L2 не наблюдается. Сценарии initial queue, cancel ahead/behind, hidden liquidity, partial fills и ack/cancel latency закрепить до17октября; касание цены не равно fill. В глубине15 выход уровня из видимой книги не равен отмене всей очереди: перестать считать точный queue там, где её нельзя восстановить.
4. Полный15мин horizon/постхвост, markout и adverse selection нужны даже для ещё не исполнившихся заявок/частичных fills; отсутствие не заменяется0. Для оборотного робота показать executable turnover, costs, gross/net per notional, inventory mark-to-market и tail, а не только число касаний.
5. All-in4bp основной и8bp стресс — ранее заявленные исследовательские сценарии. Отдельно maker/taker fee/slippage/funding; не двойной счёт. Реальную индивидуальную ставку/возврат по публичному стакану подтвердить нельзя.

До нового расчёта зафиксировать размер/стороны котирования, TTL15мин, шаг, inventory limits, latency/queue scenarios, terminal liquidation и критерий отказа. Этот экспорт сам по себе не разрешает ордера, запуск/изменение ботов или Windows-сборщиков. Ожидаемый первый результат — доказательство пригодности replay и диапазон стоимости исполнения; прибыльность пока не установлена.
