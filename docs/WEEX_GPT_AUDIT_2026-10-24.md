## Общий бюджет заявок: почему одного «185 +15» недостаточно

Запрет новых входов при нехватке мест нужен. Но «тейки ставятся всегда» технически неверно: заполненная биржа отклонит иTP. Тейк — выход по цели, не ограничитель убытка.

Нужен один механизм допуска для Grid, Trend и команд:

1. Полное свежее покрытие всех заявок/символов, включая чужие. Отдельно подтвердить, входят ли обычные, условные и trailing заявки в один конкретный лимит. Первая страница не равна всем ордерам.
2. Резерв неизвестных pending до подтверждения исхода. ACK отмены сам по себе не освобождает резерв.
3. Общая фаза сверки fills и восстановления TP/SL перед ВСЕМИ новыми входами. Нерешённый дефицит выходов запрещает новую экспозицию.
4. Резерв ещё не поставленных выходов по частичным исполнениям и уже стоящим входам; ручной/операционный запас отдельно.
5. Если надо освобождать места, по согласованному алгоритму отменять только СВОИ увеличивающие риск входы, сверив fills и завершение отмены. Не трогать чужие заявки и существующие выходы.
6. Метрики: использованные/допустимые места, покрытие, unknown intents, число/объём/возраст TP/SL-дефицита, свежесть сверки, причина запрета. «Цикл жив» не означает «все выходы подтверждены».

Консервативный инвариант: active_all + unknown_new_intents + reserved_exit_debt + extra_commitment_from_new_entry + manual_headroom <= effective_limit. Члены не должны пересекаться. Полный fill входа может освободить место; partial оставляет parent и добавляет TP. Поэтому нельзя механически считать 2 места на каждый вход или считать заявки через max_lots. При неполном свежем счётчике запрещать новые входы и явно показывать degraded, сохраняя восстановление уже существующей экспозиции.

15/200=7.5% — лишь исходный инженерный запас. Лимит частоты запросов и максимум одновременно открытых заявок различаются. [Официальная WEEX Access Restrictions](https://www.weex.com/api-doc/products/futures/QuickStart/AccessRestrictions) описывает ORDERS по userId/интервалу; это не подтверждение cap200. [Trade API](https://www.weex.com/api-doc/catalog/core-trading-futures/api/rest-api/transaction-api) описывает страницы до 100 и отдельные виды ордеров. Проверенные страницы не подтверждают постоянный универсальный cap200 или привилегиюTP. Нужны обезличенный код/текст отказа и контракт используемой версииAPI; без увеличения риска ради теста.

## Дополнительные воспроизведения: отчёты и надзор

### G1. Картинка блокирует срочный текст

app_runner.py:1142–1156 сначала собирает report и ВСЕ maps, затем send_message. Fake render_map бросает исключение→текстов 0, state commits0. Длительный сбой свечей/рендера подавляет уведомление, хотя событие известно.

Исправление: короткий текст первым, независимо от карт/полного отчёта/котировок. Долговечная очередь доставок event_id×recipient×component, состояние риска отдельно от доставки. Картинка — отдельная попытка.

### G2. Ложное возобновление

grid_report.risk_events:202–209 считает снятие подстроки «потолок» возобновлением. TEST2 ч на потолке→blocked='пауза оператором': получено «снова ставит входы — тейк освободил место». Не было ни тейка, ни принятой новой заявки.

Исправление: проверять entry_allowed и подтверждённую причину; при другой блокировке писать «потолок снят, действует пауза». Режим, сверка позиции, бюджет и stop оператора независимы.

### G3. Неизвестное не равно восстановлению

grid_report.py:80–102: при price=None bag остаётся 0, error не устанавливается. risk_events:210–215 исключает нечитаемые строки и может снять гистерезис. Synthetic−150→учёт недоступен→тот же−150 даёт два пинга вместо одного эпизода; подтверждённого улучшения не было.

Исправление: стоимость unknown/непрочитанный учёт→неполный отчёт, coverage, возраст последнего подтверждения; не снимать latch по неполным данным. Не печатать неизвестный итог как 0.

### G4. Первая задача не изолирует задержки

_run_regime_watch:1107,1111 вызывает синхронные сборку/HTTP/рендер внутри async. Fake card с 60ms blocking sleep задержала независимую probe: card_begin→card_end→probe. Это синтетическая демонстрация, не Mac latency.

БлокирующийI/O вынести в ограниченный worker, вычисления/рисование отдельно от исполнения. Ограниченная очередь, singleflight/cache для/map, дедлайны, lag P50/P95/P99. Не плодить daemon threads на повторные команды. Отмена asyncio task не останавливает уже работающий thread. [Документация asyncio.to_thread](https://docs.python.org/3/library/asyncio-task.html#asyncio.to_thread).

### G5. Кто следит за исполнителем

app_runner.py:1837,1866–1887: critical_tasks={polling,orchestrator,stop}; grid-task вне набора. При его выходе приложение остаётся, логирует и не перезапускает эту задачу. Это статический факт, не доказательство падения наMac.

Нужны degraded health по last successful tick и покрытию выходов, оповещение и проверенный recovery. Слепой restart опасен: unknown orders требуют сверки, межпроцессный lock должен держаться до завершения старых workers.

### G6. Доставка анализа не равна его проверке

regime_watch.py:388–399 обрезает story до 4096 и отмечает отправленной. Полный неизменяемый текст/собственный future anchor не сохранены. После успеха карточки неуспех story уже не повторится штатным вызовом: CARD_STATE закрывает дату до _send_story.

Исправление: note_id, точный текст/hash, actual created/sent; отправка частями без потери заключения. Независимые повторы story/карточки/карты. Человеческий тезис оценивать не раньше его фиксации/доставки; числовые признаки — от собственного freeze. Без однозначной гипотезы не писать «угадали».

### G7. Чего не доказывает «0 из 326»

В публичном отчёте median fill→TP23s, p90=54s,0/326 случаев достиженияTP за задержку. Даже при независимых идеальных испытаниях upper95% для 0/326:1−0.05**(1/326)=0.9147%. Это не доказательство нулевой цены задержки; зависимость/грубая траектория делают пример оптимистичным.

Нужны venue, принятые заявки, bid/ask/очередь, partial fills, отмены/отказы/fees. Более частые свечи не восстанавливают очередь. Измерять fill→detection→accounting→acceptedTP и длительность/объём exit debt, adverse selection; не выбирать архитектуру только по средней задержке.

## Что должно заменить «много линий и уверенный рассказ»

Основной экран должен отвечать на вопросы:

- Свежесть каждого источника и полнота покрытия. Время строки/tv не равно времени сверки биржи.
- Изменения за ОДИНАКОВОЕ закрытое окно: цена, spot trade-delta, perp trade-delta, OI в исходных единицах и отдельно USD-переоценка, funding с интервалом, actual liquidations с coverage.
- Согласованность и противоречия, две совместимые интерпретации; без выдуманной идентификации стороны по OI.
- Исход предыдущей заранее записанной гипотезы и её неподтвердившиеся ожидания.

Статус ботов отдельно: SMA «разрешаетLONG» — только правило режима, не подтверждение здоровья/достаточности ордерных мест. Средняя без fees/funding не полная безубыточность, расстояние вATR не вероятность безопасности.

Оперативные e/t/a после TTL скрыть/серить с «снимок на...». Старый контекст можно пунктиром, но не как подтверждённые стоящие сейчас заявки. БиржаWEEX на Bybit-графике должна быть явно обозначена. Pine не заменяет live-сверкуMac.

Пример структуры, НЕ текущие данные/сигнал:

«Закрытые данные наTUTC, окно 4 ч; coverage полное либо перечислены пробелы. ЦенаX→Y, объёмA→B, spot trade-deltaC→D, perp trade-deltaE→F, OI G→H, fundingI→J. Что согласуется/противоречит:... Рабочая интерпретация..., альтернативно... Усилит..., ослабит... Прежняя note_id: путь через 15/60/240/1440m..., исходная гипотеза была/не была однозначной; PENDING/MISSING отдельно».

Rolling24h изменение не новый поток. Book-delta не trade-delta. Modelled карта не actual liquidations. Суточная карта не доказывает исполнение мейкера/цену оборота.

## CoinGlass: решение сейчас

Согласен с «проверенной добавочной пользы нет». Не согласен с «до 2027 вообще ничего нельзя проверить». Нельзя переобъявить результат замороженного C1; можно исправить качество/UI и провести ОТДЕЛЬНЫЙ заранее заданный пилот на будущем.

- dr-3 даёт частоту касания по расстоянию/ATR/горизонту. Эффект strength/zonesCG в этом не проверен. Это не вероятность отскока/направления/сделки.
- Сначала admission/recovery C1. Старые записи не переписывать: отдельное quality-приложение с исходными hashes и объяснением нарушений.
- C1 со своим планом сохранить.108/5/4 — reported-only;108 снимков не означают непрерывные 108 часов. По датам 18–24.10 span≈6 дней; intervals/gaps неизвестны.
- 108/24=4.5 — только условная арифметика неперекрывающихся 24h окон при равномерных hourly anchors, не оценка реальной длительности или effective n. Календарных кластеров пока мало.
- Предлагаемый дополнительный план ниже:42 будущих дня,4h окна, один primary contrast, geometry/ATR/time-matched baseline, frozen settings/hashes, все unknown/abstention сохраняются. Точный старт и пороги ещё согласовываются; ничего не запущено. Итог при малой мощности — «неопределённо».
- Modelled near-field±3% нельзя восстановить из actual-liquidations CSV: это разные признаки. Исторический actual-liq imbalance тестировать отдельно под другим названием.

Оценивать добавочный эффект к price-only baseline, неопределённость, calibration/proper scores, например Brier; учитывать календарные кластеры и отбор вариантов. [Gneiting–Raftery](https://sites.stat.washington.edu/people/raftery/Research/PDF/Gneiting2007jasa.pdf) — оценка вероятностей; [Bailey et al.](https://www.davidhbailey.com/dhbpapers/backtest-prob.pdf) — переобучение при выборе бэктестов. Здесь рекомендация — ограничить число гипотез и оставить нетронутое будущее, а не добавить модное название метода.

### A1: контрпример и относительные позиции топов

Наблюдения «цена +2%, OI 100→101» совместимы и с агрессивным покупателем нового long против пассивного нового short, и с агрессивным продавцом нового short против пассивного нового long при росте цены на других сделках/перестановке ликвидности. Для двух наблюдаемых агрегатов результат одинаков, вывод об инициаторе разный. Поэтому OI не доказывает именно открытие лонгов/шортов.

`story.top_line` математически правильно переводит L/S в долю long: `L/(L+S)=r/(1+r)`. Но слово «добавили лонгов» из изменения отношения также не следует. Например, L=100,S=100 → L=100,S=80 даёт L/S 1→1.25 и долю 50→55.56% без единого добавленного лонга. Обратный сдвиг возможен без закрытия лонгов. Писать «доля long выросла/уменьшилась среди top trader positions Binance», а не «X% трейдеров стоят в лонгах» и не переносить это на весь рынок.

Funding — цена удержания/платёж между сторонами за явно заданный интервал; положительная/высокая ставка сама по себе не измеряет плечо и не доказывает перегрев. Агрессор — поток исполнений, modeled CoinGlass near-field — распределение модели; эти величины не взаимозаменяемы.

### A2: воспроизводимые числа

Синтетическое окно A..A+5m: ожидается 5 минут, API-заглушка возвращает только A и A+4m, их high=low=100. Коридор 95–105, уровень 105. Текущий `_forecast_progress` возвращает:

### A4: recovery

После записи fixes исключение klines/q_vector попадёт в `collector.main:301–302`, сборщик продолжит и вызовет `c1.evaluate:321`. Та вызывает close_missing, но `c1.py:321` объединяет slots из registry и fixes, поэтому слоту с одним fix нечего дописывать. На следующий день выбирается новый slot, старый так и не возвращается. В tests `test_close_missing_fills_only_empty_past_slots` текущий пропуск fix-only даже закреплён как expected; нужна отдельная проверка interrupted/incomplete slot, а не слепое удаление защиты от работающего процесса.

Регрессия: создать только fixes для первого назначенного утра; после дедлайна и завершения данного процесса close_missing/recovery обязана оставить 1 финальный/явно pending registry slot, не 0. Добавить отказ q_vector сразу после durable fix, рестарт и сохранность первоначальных границ/run ID. Не обозначать fix как missing_snapshot: снимок был, незавершён прогноз.

## Калибровка dr-3: что на самом деле проверено

`day_range.py:_compute` рассчитывает шанс касания как частоту превышения расстояния `abs(level−P_ref)/ATR` в исторических up/dn-максимумах. strength CoinGlass нигде не участвует. Для случайного/ручного уровня на той же стороне с тем же расстоянием вернётся ровно тот же шанс. Оценка размаха может быть полезна, но это нулевое доказательство добавочной ценности карты.

`_validate` (`day_range.py:115` и далее) делит дни на раннюю и позднюю половины, проверяет фиксированную фазу 08:01, 2 стороны×7 расстояний на день. Brier сравнивается с одной константой по всем расстояниям: это очень слабый baseline. Выигрыш над константой прежде всего подтверждает, что близкие уровни касаются чаще дальних. Он не сравнивает CoinGlass с price-only уровнями той же геометрии. Дни — единицы неопределённости; 14 запросов на день не 14 независимых наблюдений.

Числа 10/31/54/76/88% в сообщении — нельзя независимо пересчитать без frozen NPZ/manifest и проверочных исходов. Даже если reliability bins точны, на графике надо подписывать: «историческая частота касания при таком расстоянии/ATR, горизонт до ...; эффект зоны не проверен». Это безусловная частота от anchor утра, а не обновлённая вероятность остатка дня. Упавшая цена, уже случившийся touch и оставшиеся 2 ч изменяют условную задачу.

Две односторонние 90% квантили не дают 90% совместного коридора. Код уже печатает отдельное фактическое joint coverage и фазу 08:01; это следует сохранить. Не рисовать рядом с зоной числа без названия эксперимента, anchor/end и оговорки ATR-only. Скрыть CG по умолчанию либо отдельная research галочка, без магнита/торговой рекомендации.

Год выбран протоколом, не физической необходимостью. C1 менять, останавливать по текущему результату или объявлять успех раньше 23.10.2027 нельзя. Но ждать год ради исправления качества/UI и отдельного exploratory/futility теста не нужно.

## Near field ±3% и исторические ликвидации — разные признаки

Нельзя восстановить историю modeled near-field из фактических liquidations CSV: первое оценивает ещё не исполненные модельные зоны/силу вокруг цены, второе содержит уже произошедшие события. Исправление bybit side labels не создаёт отсутствовавшие исторические карты. Actual-liquidation imbalance можно отдельно тестировать на его собственной истории, но это другая гипотеза.

Для реального near-field prereg один continuous признак `short_share−0.5` (или ровно заранее выбранное преобразование), horizon4h, target/baseline и direction до расчётов; контроль расстояния зон/ATR, past return/realized volatility, часы, настройки/coverage. Forward split по календарю, purge горизонта между train/test, inference по дням/неделям; не discretize/перебирать ±1/2/3/5% после исходов. Добавочную ценность оценивать относительно price-only baseline на untouched future, а не отличиям raw hit rate. Неизвестный lag остаётся неизвестным, age screenshot не provider lag.

## Как превратить это в полезную аналитику

В основном экране оставить факты, непосредственно меняющие оценку риска/работоспособности: свежесть+coverage; account-wide order slots и долг по защитным заявкам; какая именно защита и когда сработает; net-cost exposure по доступному учёту; отдельно путь исполнения и отключения. SMA разрешает режим, но не подтверждает здоровье процесса.

Для рынка — один короткий связный абзац по фиксированному anchor: закрытые данные на T, цена/spot trade-flow/perpetual trade-flow/OI-native/funding/actual liqs и определения окон. Сопоставить противоречия (цена вниз при сокращении OI и spot продаже; actual long liquidations подтверждают только forced-close компонент), назвать две совместимые причины, описать проверяемую будущую гипотезу без ложного процента. Перед новым абзацем: исход прошлой заранее сохранённой гипотезы через 15/60/240/1440m, MISSING/PENDING как статусы; ни прежний текст, ни timestamp не менять.

Пример структуры, не актуальный рынок и не торговый сигнал:

«Закрытые данные на 08:00 UTC: за сопоставимые 4 ч цена X→Y, OI в контрактах A→B, spot aggressor delta C, perp delta D, funding за 8 ч E. Цена и spot-продажи согласуются, а падение OI допускает закрытие плеча; определить только лонги/шорты по OI нельзя. Из фактических ликвидаций за то же окно F/G виден forced-close компонент, не все сделки. Рабочая гипотеза: ..., альтернативно ...; через 4 ч проверим ... . Предыдущая запись: ...→фактический путь; данных не хватило/тезис ослаб/не был однозначно задан».

`story.py` сейчас не сохраняет полный неизменяемый narrative и anchor собственной отправки. `brief.build` логирует другую краткую rec.verdict; `brief.yesterday_check` имеется, но новый `story` его не вызывает, а проверка 3fixed горизонтов отсутствует. Поэтому требование «смотреть, куда потом шёл рынок и что изменялось» пока не выполнено только добавлением рассказа и таблицы маршрутов.

## Два коротких теста регрессии для переноса

Эти тесты проверяют правильный инвариант и **падают на проверенном SHA**. После исправления должны пройти. Извлекаются только чистые функции из grid_report.py: приложение не импортируется, сеть/счёт/state/ключи не читаются. Запускать после просмотра кода из корня тестируемой копии.

```python
import ast
from datetime import datetime, timezone, timedelta
from pathlib import Path

def clean_risk_functions():
    p = Path("services/grid_report.py")
    tree = ast.parse(p.read_text(encoding="utf-8-sig"))
    selected = [n for n in tree.body
                if isinstance(n, ast.FunctionDef)
                and n.name in {"_m", "risk_events"}]
    assert len(selected) == 2
    scope = dict(datetime=datetime, BAG_LEVELS=(100., 250., 500., 1000.),
                 THR_LEVELS=(3., 1.5), RESUME_MIN_CAPPED_S=3600,
                 RESUME_EVERY_S=21600,
                 SHORT={"BTCUSDT": "BTC", "ETHUSDT": "ETH"})
    exec(compile(ast.Module(body=selected, type_ignores=[]), str(p), "exec"), scope)
    return scope["risk_events"]

def fake_row(blocked="", bag=0., error=""):
    return dict(name="TEST", sym="BTCUSDT", lots=3,
                blocked=blocked, bag=bag, error=error)

T = datetime(2026, 10, 24, tzinfo=timezone.utc)

def test_pause_is_not_resume():
    risk_events = clean_risk_functions()
    _, state = risk_events([fake_row("достигнут потолок позиции")], {}, {}, T)
    events, _ = risk_events([fake_row("пауза оператором")], {}, state,
                           T + timedelta(hours=2))
    assert not any("снова ставит входы" in e for e in events)

def test_unreadable_state_does_not_rearm_same_loss():
    risk_events = clean_risk_functions()
    first, state = risk_events([fake_row(bag=-150)], {}, {}, T)
    assert any("Мешок" in e for e in first)
    _, state = risk_events([fake_row(error="JSONDecodeError")], {}, state,
                          T + timedelta(minutes=5))
    again, _ = risk_events([fake_row(bag=-150)], {}, state,
                          T + timedelta(minutes=10))
    assert not any("Мешок" in e for e in again)
```

Для E1/E2/E3, R1–R5 и A2–A4 синтетические входы и ожидаемые инварианты описаны в соответствующих пунктах. Полные локальные воспроизведения выполнены; архивов/сырых данных и отдельных запускаемых пакетов в этот коммит нет.
