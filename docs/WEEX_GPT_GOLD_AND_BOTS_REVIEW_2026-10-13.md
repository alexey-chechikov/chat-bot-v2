## 2. WEEX: два дефекта торгового движка с приоритетом P1

### W1. Неизвестная деталь ордера позволяет поставить второй тейк

Источник: [обычная обработка отсутствующего TP, `engine.py:943`](https://github.com/alexey-chechikov/chat-bot-v2/blob/8f093390b53615f5cb37545ffca5441443982d59/services/weex_grid/engine.py#L943). Аналогичные сырые ответы есть в обработке entry на 901–905 и отмене несовпадающего TP на 928–936. [Защищённый `_detail`, строка 1010](https://github.com/alexey-chechikov/chat-bot-v2/blob/8f093390b53615f5cb37545ffca5441443982d59/services/weex_grid/engine.py#L1010) уже проверяет идентификатор и явный статус, но обычные ветки его обходят.

Воспроизведение: бот имеет LONG `0.0001`; старый TP остаётся `NEW`, но один ответ списка открытых ордеров его пропустил. Деталь `{}` приводит к удалению ссылки на старый TP и выставлению нового. Получены **два живых TP суммарно `0.0002`**. Ответ с чужим `orderId`, `status=FILLED, executedQty=0` даёт тот же результат.

В отдельном условном примере ручной LONG `0.0050` делит сторону с лотом бота: оба TP исполняются, позиция меняется `0.0051 → 0.0049`; лишние `0.0001` закрыты за пределами лота бота. **Это не утверждение о текущем ручном SHORT оператора:** он на другой стороне. Поддельная биржа принимает оба ордера; фактическое принятие этой комбинации WEEX отдельно не измерялось. Код посылает лишний ордер, а `reduceOnly` ограничивает общую позицию стороны и само по себе не устанавливает владельца закрываемых единиц.

**Спецификация исправления:** один классификатор детали во всех ветках entry/TP/stray/flatten/release. Совпадающий ID, явный допустимый статус, проверка ожидаемых symbol/position side и накопленного исполнения. `{}`, чужой ID, отсутствующий/неизвестный статус — `UNKNOWN`: сохранить ордер и курсор на диске, не ставить замену, не освобождать владение, повторить сверку. Подтверждённое частичное исполнение применять один раз через долговечный cumulative cursor. Замену разрешать только после подтверждённого завершения старого ордера и вычисления остатка.

Приёмка: пропавший из одного списка живой TP + `{}`/чужой ID/неизвестный статус оставляет ровно один TP; повтор тика и рестарт не добавляют выход. После настоящего терминального статуса исполнение учитывается один раз, замена покрывает только остаток. Такой тест дополняет уже проходящий `test_manual_short_untouched_by_regime_close`: его четыре мутации не покрывают эти ответы биржи.

### W2. Живой stray может исчезнуть из учёта до передачи оператору

Источник: [`_process_strays`, `engine.py:644`](https://github.com/alexey-chechikov/chat-bot-v2/blob/8f093390b53615f5cb37545ffca5441443982d59/services/weex_grid/engine.py#L644).

Воспроизведение: ранее отменяемый SHORT TP всё ещё `NEW` и записан в `strays`; деталь `{}` удаляет его из наблюдения. Затем `release_side` очищает SHORT-лоты и сообщает «передано оператору», хотя прежний тейк бота остаётся живым. Защиты непосредственно внутри release недостаточно, если предыдущий путь уже забыл ордер.

**Спецификация исправления:** `UNKNOWN` stray сохраняется до подтверждённого терминального статуса; передача невозможна при unresolved entry/TP/stray/pending/flatten. После отмены досверить исполнения, зафиксировать остатки, сохранить событие передачи, затем объявить успех. Нулевой остаток тоже требует события передачи. Приёмка: живой stray + `{}` не исчезает после повторов и рестарта, событие успеха не создаётся; после подтверждённой отмены/исполнения передача завершается однократно.

## 3. Ответы на шесть вопросов о WEEX

### 1. `account_now`: где ещё возможен ложный «ок»

Пороги 60/180 секунд разумны как диагностика процесса с 10-секундным циклом и 60-секундной паузой после ошибки. Проверки `halted`, чужого ID и неполной истории в переполненном секундном окне в пробах работают. Но свежесть процесса не доказывает успешное сопровождение.

| Дефект | Проверенный контрпример | Рекомендация и приёмка |
|---|---|---|
| mtime обновляется до успешного окончания tick | `_orphans` сохраняет состояние на `engine.py:636/705`; три последующих падения `_side` освежают файл. Скрипт пишет «цикл жив», итог `ок`, exit 0 | Отдельные `last_attempt`, `last_success`, `last_error/phase`. `last_success` обновлять только после завершения прохода. Три падающих прохода не освежают успех; неизвестное сопровождение исключает `ок` |
| Отсутствующий CID считается ручным ордером | Совпадающий orderId, но нет `clientOrderId`: сделки бота скрыты как ручные, exit 0 | Отсутствующее поле — неизвестное владение. Использовать долговечный реестр собственных ID/CID; без доказанного владельца exit 2. Тесты missing/null CID и иной версии схемы |
| История `null` принимается за пустую | `response or []` даёт ноль сделок и exit 0 | Проверять успешную схему ответа, обязательные поля и полноту страниц. `null` — ошибка чтения; только подтверждённый пустой список означает ноль |
| Нет события передачи стороны | Граница передачи `н/д`, но найденная сделка бота не мешает итоговому `ок` | Сохранять передачу даже при нуле лотов, с временной границей биржи. Нет границы — после передачи результат неизвестен; пограничную секунду отдельно досверять |
| SMA без проверки свежести | Последняя дневная свеча старше текущей на 101 день всё ещё даёт «вчерашнее закрытие», ЛОНГ и `ок` | Использовать общую с движком проверку вчерашнего UTC дня, непрерывности, конечных цен и прогрева. Ошибка режима участвует в итоговом статусе |

Ссылки: [`account_now.py:124`](https://github.com/alexey-chechikov/chat-bot-v2/blob/8f093390b53615f5cb37545ffca5441443982d59/research/weex/account_now.py#L124), [разбор владельца, строка 93](https://github.com/alexey-chechikov/chat-bot-v2/blob/8f093390b53615f5cb37545ffca5441443982d59/research/weex/account_now.py#L93), [режим, строка 72](https://github.com/alexey-chechikov/chat-bot-v2/blob/8f093390b53615f5cb37545ffca5441443982d59/research/weex/account_now.py#L72). Поля orderId/clientOrderId присутствуют в [официальной схеме детали WEEX](https://www.weex.com/api-doc/catalog/core-trading-futures/api/rest-api/transaction-api#get-order-info-user_data); отсутствующее поле нельзя считать доказательством ручного владельца.

Дополнительно: клиент заканчивает чтение open orders после десяти полных страниц по 100 без флага неполноты (`client.py:106–114/152–160`). Для текущих маленьких сеток переполнение не установлено, но чистый вердикт обязан отличать полный ответ от достигнутого лимита.

`errors_today.py` доказывает только наличие ранней записи, а не непрерывность покрытия. В пробе старый `errors.log` и свежий ERROR в console дали `ERROR 0` без предупреждения: console используется для WARNING, но его ERROR игнорируется. Нужно сверять и дедуплицировать ERROR из обоих источников, отдельно указывать начало хранения, пропуски и недоступные файлы. Реальный DNS-эпизод без вложения не перепроверен.

### 2. Отсутствие TP среди открытых — достаточно ли для orphan check

**Для предварительной тревоги — да; для доказанного отсутствия защиты — нет.** [`orphan_check.py:54`](https://github.com/alexey-chechikov/chat-bot-v2/blob/8f093390b53615f5cb37545ffca5441443982d59/research/weex/orphan_check.py#L54) не запрашивает деталь. Проба: TP полностью исполнился, остаток позиции бота на бирже ноль, локальный лот ещё не обновлён — скрипт объявляет один лот без тейка. Существующий совет повторить через 10–20 секунд уместен, но не заменяет проверку исполнения.

**Рекомендация:** каждому отсутствующему TP запросить проверенную деталь и вывести один из статусов: исполнение ждёт учёта; частичное исполнение с остатком; отменён/отклонён и остаток без TP; жив, но пропущен списком; неизвестен. Проверять оставшийся объём, сторону, цену и `reduceOnly`, не только наличие ID. Приёмка: FILLED + нулевой остаток не объявляется позицией без выхода; UNKNOWN не выдаёт чистое `ок`; частично исполненный TP защищает только свой настоящий остаток. Сам проверочный скрипт ордера не ставит и не отменяет.

### 3. `sides` + непереданные стороны с остатками — верно ли

**Для текущего сопровождения верно, для накопленного PnL недостаточно.** [`pnl_reconcile.py:39`](https://github.com/alexey-chechikov/chat-bot-v2/blob/8f093390b53615f5cb37545ffca5441443982d59/research/weex/pnl_reconcile.py#L39): после окончательного закрытия удалённая из `sides`, но непереданная сторона исчезает из сверки вместе с её старой ошибкой денег.

Проба: бывшая SHORT-сторона полностью пуста, биржевые сделки показывают `$5`, учёт `$7`; сверяется только LONG и итог совпадает. Это искусственные числа.

**Рекомендация:** постоянные интервалы владения и реестр собственных сделок/ID, независимые от текущих разрешённых входов. Сверять все исторически принадлежавшие боту стороны, включая пустые. Для передачи — до границы сверять старого владельца, после границы искать остаточную активность бота. Приёмка: удаление SHORT из `sides` и последующее обнуление позиции не скрывают расхождение `$2`; ручные сделки после передачи не попадают в доход бота. Missing CID/null history обрабатывать как в вопросе 1.

### 4. Окно гонки `repair_frozen_1m`

**Окно осталось.** [`write_atomic`, строки 95–106](https://github.com/alexey-chechikov/chat-bot-v2/blob/8f093390b53615f5cb37545ffca5441443982d59/research/weex/repair_frozen_1m.py#L95): после успешной проверки размера/mtime и до `os.replace` писатель может дописать строку. В пробе строка реально дописана в эту точку; замена вернула успех и потеряла её. `fsync` и атомарная замена не объединяют проверку и дозапись в одну транзакцию. Открытый append-дескриптор может также продолжать писать в прежний файл после замены.

**Рекомендация:** общий межпроцессный lock, используемый и gapfill, и repair, на чтение/проверку/замену; писатель под lock заново открывает актуальный путь. Альтернатива — согласованная остановка писателя с закрытием дескрипторов или неизменяемые версии данных с атомарным manifest. Уникальные временные файлы; 1m и производный 1h одной версии. Один дополнительный stat окно не устраняет.

Вторая ошибка: [`fix_hours`, строка 166](https://github.com/alexey-chechikov/chat-bot-v2/blob/8f093390b53615f5cb37545ffca5441443982d59/research/weex/repair_frozen_1m.py#L166) проверяет число строк, а не уникальную непрерывную сетку времени. 60 строк с дубликатом минуты 0 и отсутствующей минутой 17 приняты за полный час. Требование: ровно 60 разных UTC-меток `hour + k×60000`, `k=0..59`, без дубликатов и с валидными OHLCV. Приёмка: конкурентная дозапись сохранена либо операция отменена; час 59 unique/60 rows отвергнут; принудительное завершение между публикацией 1m/1h не оставляет незаметно смешанные версии. Поправка gapfill `now−2 минуты` полезна, но это другой дефект.

### 5. Стоп, фандинг и «не закрывать в минус»

**Тейк и дневная SMA не ограничивают денежный убыток.** Mac может лежать; дневная смена режима допускает большой ход до закрытия и гэп. Порог сегодняшнего закрытия из `account_now` — не максимальный убыток и не биржевой аварийный стоп. Значения −12.3%/−10.6% из присланного состояния здесь не проверены.

Рекомендую следующую спецификацию, сначала для тестов и согласования оператором:

1. До нового входа задать общий денежный бюджет потерь стратегии `B_total` от фиксированной точки equity `E_ref`, цену аварийного выхода `S` и бюджет всего счёта с ручными позициями. Доступный бюджет дальнейшей потери: `B_remaining = max(B_total − max(E_ref−E_now,0), 0)`; точку отсчёта не обновлять автоматически после убытков. Для LONG риск от **текущего equity**, с текущей mark price `M`, оценить как `Σ q_i×max(M−S,0) + комиссии/проскальзывание выхода + резерв фандинга`. Итоговый PnL от цены входа считать отдельно. Новый объём — округлённый вниз минимум из свободного `B_remaining` после резервирования существующего риска, лимита позиции и маржи; риск новой единицы считать от ожидаемого исполнения входа до аварийного выхода с затратами. При неизвестной позиции/защите новые входы запрещены. `B_total` нельзя вывести из потолка `$15k` без капитала и стопа.
2. После исполнения входа подтвердить на бирже аварийный выход на принадлежащий боту остаток; не заменять его обещанием локального цикла. Требуется проверить поддержку, trigger price и правильную сторону инструмента WEEX. Если защита не подтверждена, входы блокируются и выполняется заранее согласованный аварийный сценарий. Поведение при Mac/offline не зависит от Mac.
3. Рыночный выход по SMA, TP и аварийный выход связать с одним долговечным намерением и учётом cumulative fills. Рестарт/потерянный ответ/частичное исполнение не добавляют повторное закрытие. При исполнении защитного ордера остаток и конкурирующие выходы досверяются. Рыночный stop при гэпе всё равно может превысить плановый `B`; это не гарантия цены.
4. На смешанной ручной и ботской LONG-стороне `reduceOnly` не доказывает отдельную собственность объёма. Для независимого ограничения риска нужен отдельный субаккаунт либо строгий согласованный учёт вмешательств. Переданный ручной SHORT также использует маржу общего счёта.
5. Фандинг вести отдельным денежным ledger по времени, стороне, объёму и реально начисленной сумме. Если общая сторона содержит ручной объём, деление по позиции бота на момент начисления — явно обозначенная аллокация, а не отдельное списание биржи. Возврат партнёра отражать после фактического зачисления. Итог: реализованный PnL, комиссии, фандинг, нереализованный результат, возвраты — отдельно и вместе.

Приёмка: офлайн Mac; отказ постановки защиты; partial fill; потерянный ответ закрытия; simultaneous TP/stop/SMA; рестарт в каждой фазе; ручное частичное закрытие. Нет двойных выходов и необозначенного остатка. Ограничитель [`portfolio.py:62`](https://github.com/alexey-chechikov/chat-bot-v2/blob/8f093390b53615f5cb37545ffca5441443982d59/services/weex_grid/portfolio.py#L62) считает учётную стоимость и резерв заявок ботов, не весь счёт и не расстояние до ликвидации.

Установка настоящего ограничителя потерь несовместима с буквальным запретом когда-либо закрывать в минус. Моё предложение: запрет запрограммированных убыточных выходов не должен отменять утверждённый аварийный риск и смену режима. Оператору нужно выбрать это правило явно перед изменением живых ботов; текущий аудит ничего не переключает.

### 6. Контроли, движок и GinArea

**999 повторов не устраняют несовпадение моделей и экспозиции.** Ранги 0.23/0.12 не воспроизведены этой проверкой; контроль «то же время в рынке ±1 п.п.» всё ещё нужен. Число повторов отвечает за разрешение Monte Carlo, не за корректность сравнения.

- [`regime_grid.load`, строка 42](https://github.com/alexey-chechikov/chat-bot-v2/blob/8f093390b53615f5cb37545ffca5441443982d59/research/weex/regime_grid.py#L42) проверяет число дневных closes, но не полноту дней. Файл со 101 днём и **одной минутой в каждом** проходит требование «100 полных дней». Нужны проверки временной сетки, OHLCV, завершённых дней и причинности; неполные дни не превращать молча в полноценные closes.
- `validate_fast.py` теперь действительно фиксирует конфиг, но сравнивает старую двустороннюю сетку `.2/.21`, `qty=.0012`, cap `$4000`, без SMA. Это **не** сверка нынешней `.6/1.4`, LONG, SMA100, BTC `.0036/$12k` или ETH `.020/$2500`. Разницу 3–6% нельзя автоматически назвать допустимой: нужно объяснить её на первой расходящейся заявке и сверить fills, fees, остатки и рыночные закрытия текущей конфигурации.
- [`ginarea_regime_check.py:40/76`](https://github.com/alexey-chechikov/chat-bot-v2/blob/8f093390b53615f5cb37545ffca5441443982d59/tools/ginarea_regime_check.py#L40): SPEC накладывается на полный базовый объект клона; неуказанные `so/ioo` наследуются. Значит, влияние Dynamic `.4/.06` не исключено. Его знак и размер без фактического readback и прогонов неизвестны. Хранить полностью эффективный конфиг, проверить каждый значимый параметр после установки, сравнить отдельные заранее определённые конфиги смещений на одинаковых данных. В этом аудите внешние тестовые боты не перенастраивались.
- Ключ пропуска содержит **даты**, а не точные timestamps, и не содержит полный SPEC/data hash. В пробе окончания 13.10 в 08:00 и 12:00 дают одинаковый ключ. При изменении `maxOp`, объёма или Dynamic старый результат также можно ошибочно переиспользовать. Требование: точные UTC endpoints + symbol + hash полного эффективного конфига + hash данных/версии движка.
- Результат свежих отдельных отрезков не равен непрерывному счёту: перенос мешка, ограничение капитала, closing fees и фандинг требуют отдельного непрерывного прогона. Рыночный источник Binance не доказывает цены/исполнение WEEX.

Приёмка исследования: неизменяемый CSV с SHA256; та же живая конфигурация в `eg.Grid` на поддельной бирже без ключей; ledger каждой заявки и fill; расхождения объяснены, не скрыты агрегатным допуском. Затем непрерывный replay с финансированием и затратами, заранее заданный holdout, случайные режимы с сопоставимыми временем LONG и занятым капиталом, сравнение чистого результата/просадки. Пока этого нет, увеличение размера BTC нельзя обосновывать прежними рангами.

## 4. Золото: вывод и фандинг

Согласно присланному результату, main A имеет net −0.510R PAXG / −0.381R XAU; B −0.451R / −0.315R. Это отрицательные результаты при выбранных прокси, модели исполнения и затратах. Они не дают положительного кандидата. Отдельный предшествующий коммит протокола, разделение proxy/native footprint и отказ выдумывать недостающую дельту — правильные элементы работы.

Но исправить нужно четыре вывода:

1. **«Эджа нет» → «проверенные варианты не прошли условия кандидата при данной модели затрат».** Исправленный gross price R PAXG A имеет CI −0.19…+0.05; footprint C/D не проверены; E имеет n8/n10, XAU E CI −0.843…+0.296. Малые отрицательные оценки могут означать отказ по операционному gate, но не доказанное отсутствие эффекта.
2. **Среднее B не является верхней границей условного C.** На синтетическом ledger с n194 и средним −0.451R, согласованном с опубликованными WR/средними выплатами B, существует подмножество n100 с +0.1475R, CI [+0.131,+0.1695], holdout +0.120. Это математический контрпример, **не найденная прибыльная footprint-стратегия**. Стоимость в R у отфильтрованных сделок также может отличаться. Порог «C обязан дать >+0.45R» нельзя вывести только из среднего B.
3. B−A по точечным net-оценкам составляет **+0.059R PAXG / +0.066R XAU**, S1 +0.095/+0.086. Оба минуса не доказывают, что VWAP ничего не добавляет. Нужен доверительный интервал разницы по общим календарным недельным блокам и последующее отдельное подтверждение, а не подбор на использованном holdout.
4. **Фандинг нельзя исключать из-за удержания ≤4 часов.** Позиция 07:45–08:15 пересекает начисление в 08:00, хотя живёт полчаса. Более того, Binance изменил интервал XAUUSDT с 8 на 4 часа с 30.01.2026 18:15 UTC, первые начисления по новой схеме — 20:00. Это официальное изменение, относящееся к большей части проверяемого XAU-периода. [Уведомление Binance](https://www.binance.com/en-TR/support/announcement/detail/55bd3594394a46daa910df5746355ff4).

Фандинг для LONG: `−qty×mark_price×funding_rate` в момент начисления; отрицательная ставка приносит LONG поступление. Поэтому отсутствие фандинга не обязательно завышает результат: знак и сумму нужно посчитать. Взять фактические времена/ставки из [Binance funding history](https://developers.binance.com/docs/derivatives/usds-margined-futures/market-data/rest-api/Get-Funding-Rate-History), сопоставить с открытым объёмом и учесть изменение equity и следующих размеров. [Правила начисления](https://www.binance.com/en/support/faq/detail/360033525031). Нужны число пересечений и итог денег/R отдельно для development/holdout и каждой стратегии. Обновлённый PnL без этого неизвестен.

## 6. Золото: контроль LVN, R и MGC

### Контроль LVN сейчас не проверяет реализованную E

[`sweep_lvn_controls.py:39`](https://github.com/alexey-chechikov/chat-bot-v2/blob/8f093390b53615f5cb37545ffca5441443982d59/research/gold/sweep_lvn_controls.py#L39) фильтрует готовый ledger B, тогда как E заново симулирует стратегию. Отказ от раннего сигнала освобождает место более позднему. Проба: B берёт сигнал hour47 с −0.9582R, E — другой hour49 с +1.7155R. Поэтому **ledger E не обязан быть подмножеством исполненных сделок B**; rank фильтра B не является rank стратегии E.

Кроме того, реальные функции контроля **на синтетических фикстурах с подменённым Market, без PAXG/XAU CSV** дали следующие контрпримеры. Частоты ниже не являются измеренным масштабом ошибки исторического исследования:

- 172/999 размещений двух одно-биновых зон теряют покрытие из-за совпадения; 338/999 меняют число непрерывных зон. Среднее 1.8278 bins / 1.6617 zones вместо 2/2. Множество свободных bins вычислено один раз и занятое место не удаляется.
- Если размещение заданных ширин невозможно, все результаты NaN, но выводится **`0/0, rank 1.000`**. При нуле валидных контролей rank должен быть `NA`, не 1.
- Профиль перерисовывается для каждой сделки. Два одинаковых сигнала одного дня с одинаковым уровнем получили разные решения о попадании в 390/999 повторов. Нулевая гипотеза случайного дневного профиля требует общего профиля для всех сигналов этого дня.

**Спецификация исправления:** заранее описанный null; та же совокупность ширин и число зон, без пересечений и нежелательных слияний; фиксированный случайный профиль на каждый день/окно, общий для сигналов этого дня. Невозможные размещения учитывать как невалидные, выводить их число и правила отбора. Для сравнения E каждый control заново прогонять через ту же stateful execution модель. Либо отдельно назвать задачу «условный эффект фильтра на фиксированном B», не сравнивая её с независимо исполненной E. Пересчитать published ranks .258/.845; реальный размер изменения без исходных профилей неизвестен.

### Разные определения R смешаны в объяснениях

В коде `R = PnL/(0.0025×equity_before_trade)`; sizing включает затраты стопа. Это R денежного бюджета. `.24%/.30%=.8` — R ценового расстояния до стопа. Например, при entry 1000/stop 997 и PAXG fees/slippage из протокола плановый риск на единицу 5.1964; условные roundtrip-затраты 2.4 дают около **0.462 бюджетного R**, а не 0.8. Пример показывает различие единиц, не историческую среднюю стоимость сделки.

Gross/net могут иметь разные entry, TP, q, cash caps и набор сделок; вычитание их средних R не выделяет только комиссию. G1 признан, но таблицы продолжают показывать capped gross A −.053 / B +.011, тогда как текст даёт corrected price R −.070 / −.005. Исправить заголовки/таблицы и опубликовать расчёт обеих нормировок на одном согласованном ledger.

ISO-week bootstrap пригоден для условного среднего по сделкам с недельными кластерами. Он не даёт CI доходности непрерывного счёта и не пересчитывает equity/размеры при повторной выборке недель. Для E вывести число непустых недельных блоков и распределение сделок; независимость блоков — предположение метода. 9,999 повторов не добавляют данных к 8–10 сделкам. В синтетическом случае восьми сделок одной недели CI вырождается; это не утверждение о реальном E-ledger.

### MGC: проверен бюджет на прокси, не MGC-стратегия

Контракт MGC — 10 унций, tick $0.10/унцию, то есть $1 за контракт. [CME](https://www.cmegroup.com/education/lessons/micro-gold-and-micro-silver-futures-product-overview). Скрипт применяет `(crypto entry−crypto stop)×10 + $3` к PAXG/XAU-сделкам. При капитале $1000 расходы $3 уже превышают бюджет риска 0.25% капитала ($2.50); для $3000/$5000 формула требует ширины ≤$0.45/≤$0.95.

Результат «0/312 и 0/139 укладываются в этот бюджет на прокси при предположенных $3» может быть верен. Вывод «реальная MGC-стратегия невозможна» из этого не следует. Нужны реальные MGC prices, sessions, roll, tick-rounded stops/entries, broker costs и margin. GC/MGC не исследованы текущим replay; прибыльность переноса также не доказана.

## 7. Какие числа удалось и не удалось подтвердить

В таблицах исследования не нашёл арифметических ошибок: n=TP+SL+TIME, development+holdout=n; взвешенные средние совпадают в пределах округления. Все 36 денежных строк согласуются с rounded WR/средними выплатами и `final−capital ≈ n×mean dollar PnL`. Кварталы main PAXG дают −159.1R против `312×−.510=−159.12R`; XAU −52.9R против `139×−.381=−52.959R` — допустимое накопленное округление.

Ошибки относятся к **смыслу и полноте чисел**: fund-free XAU net; 0/0 rank 1.000; нематченные LVN controls; gross price R против budget R; MGC proxy screen против фактического MGC. Агрегатная арифметика этих проблем не обнаруживает.

Для полного повтора нужны immutable CSV + SHA256, trade JSON со всеми timestamps, q, entry/stop/target, fees/funding, exit reason, equity/risk budget и effective config; versions/runtime, bootstrap seeds и полный вывод. Частный WEEX-пакет нужен отдельно для проверки фактического учёта и журналов, **его нельзя публиковать вместе с этим отчётом**.

## 8. Порядок доработок

1. W1/W2: общий UNKNOWN-safe обработчик детали ордеров во всех путях; новые tests. Это приоритет торгового кода. Изменения готовить изолированно, живой перезапуск — по установленному процессу оператора.
2. Исправить ложные `ок` мониторинга и историческое владение в сверке; гонку repair закрыть общим протоколом с писателем. Наличие прежних 100 passing tests не заменяет эти сценарии.
3. Определить денежный риск, аварийную защиту и правило убыточного выхода, включить фандинг в финансовый учёт. Без этого потолок номинала не является пределом потерь счёта.
4. Золото: починить данные/causality/выходы/null, добавить signed funding и единицы R, затем повторить замороженный набор на тех же данных.
