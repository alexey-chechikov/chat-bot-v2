## 2. Найденные проблемы кода и критерии исправления

Все ссылки и номера строк ниже относятся к проверенному SHA. При изменении версии сначала сопоставить актуальный код.

### F1 / P2. Сценарий доборов не учитывает потолок стоимости позиции

[tv_levels.py:156](https://github.com/alexey-chechikov/chat-bot-v2/blob/1d303fcbd76b9ff8bc2a73b48c5a4f48a7d5a8ac/services/tv_levels.py#L156) ограничивает доборы числом лотов. `max_notional_usd` не переносится в `detail` ([строка 64](https://github.com/alexey-chechikov/chat-bot-v2/blob/1d303fcbd76b9ff8bc2a73b48c5a4f48a7d5a8ac/services/tv_levels.py#L64)).

Движок перед новым входом ограничивает `max(себестоимость, текущая стоимость) + стоимость нового входа` через `max_notional_usd`: [engine.py:644](https://github.com/alexey-chechikov/chat-bot-v2/blob/1d303fcbd76b9ff8bc2a73b48c5a4f48a7d5a8ac/services/weex_grid/engine.py#L644). В `may_add` также есть блокировки, общий доступный лимит и при включении стресс-бюджет.

Синтетический пример дал девять доборов в сценарии против одного, разрешённого потолком стоимости. Это пример на искусственных данных, не сведения о живых позициях.

**Исправление:** для сценария использовать ту же семантику ограничений, что у движка. Если часть ограничений невозможно достоверно восстановить из снимка, явно отметить неполную модель и не выдавать результат за ожидаемое фактическое поведение всех сеток.

**Приёмка:** при достижении потолка стоимости следующие доборы прекращаются; в результате есть причина ограничения. На одном искусственном снимке движок и сценарий допускают одинаковое количество входов при одинаковых предпосылках.

### F2 / P2. Частичные исполнения считаются отдельными занятыми слотами

Сценарий начинает с `len(lots)` ([tv_levels.py:156](https://github.com/alexey-chechikov/chat-bot-v2/blob/1d303fcbd76b9ff8bc2a73b48c5a4f48a7d5a8ac/services/tv_levels.py#L156)), а движок считает уникальные `parent`: [engine.py:620](https://github.com/alexey-chechikov/chat-bot-v2/blob/1d303fcbd76b9ff8bc2a73b48c5a4f48a7d5a8ac/services/weex_grid/engine.py#L620). Один вход может породить несколько записей лотов при частичном исполнении.

Синтетический случай: три записи частичного исполнения одного входного ордера при потолке три. Сценарий показывает ноль новых ордеров и достижение потолка; фактически занят один логический слот, а по числу слотов свободны ещё два. Остальные ограничения проверяются отдельно.

**Исправление:** сохранить `parent` и данные об остатке текущего входа; различать число записей исполнения, логические слоты и количество новых заявок. Не присваивать всей заявке полный `order_qty`, если исполняется только остаток.

**Приёмка:** несколько частичных исполнений одного `parent` занимают тот же слот, что в движке; частичный остаток учитывается без удвоения объёма.

### F3 / P2. Следующие цены доборов не округляются к тику

Сценарий использует чистое умножение на `1 - step / 100`: [tv_levels.py:160](https://github.com/alexey-chechikov/chat-bot-v2/blob/1d303fcbd76b9ff8bc2a73b48c5a4f48a7d5a8ac/services/tv_levels.py#L160). Движок округляет LONG-вход вниз по тику: [engine.py:699](https://github.com/alexey-chechikov/chat-bot-v2/blob/1d303fcbd76b9ff8bc2a73b48c5a4f48a7d5a8ac/services/weex_grid/engine.py#L699).

Искусственный пример: первый вход `98.01`, шаг `1%`, тик `0.01`, нижний край `97.025`. Сценарий считает вторую покупку по `97.0299`; движок выставит `97.02`, до которой цена при таком крае не дошла. Получается два добора вместо одного.

**Исправление:** использовать тот же способ округления на каждом шаге и учитывать действительные параметры инструмента.

**Приёмка:** пример выше даёт один добор; на последовательности из нескольких шагов цены совпадают с ценами движка, включая пограничные случаи относительно нижнего края.

### F4 / P2. Битое числовое поле обрывает всю сборку вместо `skipped`

JSON читается внутри `try`, но преобразования `float` и разбор структуры лотов выполняются после него: [tv_levels.py:53](https://github.com/alexey-chechikov/chat-bot-v2/blob/1d303fcbd76b9ff8bc2a73b48c5a4f48a7d5a8ac/services/tv_levels.py#L53), [строка 62](https://github.com/alexey-chechikov/chat-bot-v2/blob/1d303fcbd76b9ff8bc2a73b48c5a4f48a7d5a8ac/services/tv_levels.py#L62).

Синтаксически валидный JSON с `qty: "bad"` выбрасывает `ValueError` наружу. Для некоторых неверных структур возможны `KeyError` или `TypeError`. До полного разбора сетка уже добавляется в `grids`.

**Исправление:** полностью проверить одну сетку до изменения общего агрегата. При ошибке сохранить причину пропуска, пометить результат неполным и продолжить чтение остальных сеток. Не подменять отсутствие данных нулевой позицией.

**Приёмка:** одна повреждённая сетка не скрывает исправные; число прочитанных/ожидаемых сеток и причина пропуска видны в Telegram и передаваемом Pine-снимке. Отдельно проверить случай, когда не прочитана ни одна сетка.

### F5 / P2. Возможное освобождение замка до окончания рабочего потока при остановке

`_shutdown_task` по таймауту отменяет asyncio-задачу: [app_runner.py:1595](https://github.com/alexey-chechikov/chat-bot-v2/blob/1d303fcbd76b9ff8bc2a73b48c5a4f48a7d5a8ac/app_runner.py#L1595). Проход сеток исполняется через `asyncio.to_thread(runner.tick)`: [loop.py:560](https://github.com/alexey-chechikov/chat-bot-v2/blob/1d303fcbd76b9ff8bc2a73b48c5a4f48a7d5a8ac/services/weex_grid/loop.py#L560).

Отмена ожидающей asyncio-задачи не останавливает уже выполняющийся поток. После обхода множества `pending` `_main_locked` возвращается, а `main` закрывает fd замка: [app_runner.py:1811](https://github.com/alexey-chechikov/chat-bot-v2/blob/1d303fcbd76b9ff8bc2a73b48c5a4f48a7d5a8ac/app_runner.py#L1811), [строка 1625](https://github.com/alexey-chechikov/chat-bot-v2/blob/1d303fcbd76b9ff8bc2a73b48c5a4f48a7d5a8ac/app_runner.py#L1625).

Если старый проход пережил завершение обёртки и оставшийся shutdown, новый процесс может получить замок до окончания старого потока. Таймаут отдельного API-запроса по умолчанию 15 секунд ([client.py:63](https://github.com/alexey-chechikov/chat-bot-v2/blob/1d303fcbd76b9ff8bc2a73b48c5a4f48a7d5a8ac/services/weex_api/client.py#L63)), таймаут завершения задачи — 10 секунд; один проход содержит несколько обращений. Порядок обхода `pending` не фиксирован.

**Статус доказательства:** потенциальный сценарий выявлен статическим разбором; его наступление в живом процессе не проверялось. Это не доказанный повтор инцидента 12:01–12:10. Изолированный helper в Windows не дал успешного runtime-воспроизведения и был остановлен.

**Исправление:** удерживать замок до завершения всех работников, способных отправлять ордера или писать учёт. Просто увеличить 10 секунд недостаточно для доказательства корректного времени жизни замка.

**Приёмка:** на изолированном тесте с fake `tick`, заблокированным событием, инициировать остановку; вторая копия не получает замок до реального окончания первого worker. В тесте исключить настоящие службы, ключи и биржевые вызовы. Проверить обычный stop, timeout и отмену `main`. Успешное выполнение и гарантия отсутствия пересечения должны быть отражены в ответе Claude.

В обычном проверенном пути общий HOME-lock, защита в `main`, отсутствие удаления lock-файла и закрытие fd в `finally` выглядят обоснованно. Тесты с заменой `_main_locked` не покрывают описанное завершение настоящей обёртки `to_thread`.

### Что в сценариях не признано ошибкой

Для полных исполнений без дополнительных ограничений последовательность «следующий LONG-вход от крайнего нижнего открытого × (1 − шаг)» соответствует движку с оговоркой об округлении. Ошибок знака комиссии не найдено: комиссия выхода вычитается из закрытого результата, комиссия новых входов — из расчётного мешка. Актуальность ставки и предпосылки maker-исполнения всё равно должны быть указаны, а не обещаны как гарантированные.

## 3. TradingView и /tv: предлагаемые улучшения

### 3.1. Компоновка рабочего места

Сохранить знакомую логику BTC 4ч/15м, золота и ES. Оператору показаны два варианта:

- **«Фокус на BTC»**: BTC 15м занимает около двух третей ширины и основную высоту; справа обзорные BTC 4ч, золото 1ч и ES 1ч. Основной и контекстный BTC можно поменять местами.
- **«Контекст и вход»**: привычные четыре окна; BTC 4ч над BTC 15м в широком левом столбце, золото и ES в более узком правом.

Далее: сократить чрезмерную пустоту справа; сделать сетку и режимные заливки спокойнее; сохранить узнаваемые цвета средних; при отсутствии необходимости скрыть Buy/Sell и длинную строку OHLC. Компоновку выбирает оператор; это не изменение торговой стратегии.

### 3.2. Краткая и подробная таблица

Краткий вид должен отвечать на четыре вопроса:

1. Что разрешает действующий дневной режим?
2. Сколько до порога и когда закрывается день UTC?
3. Какой следующий вход/тейк ближе всего, сколько до него процентов и какая сетка его выставила?
4. Когда обновлены данные, полны ли они и действует ли ещё прогноз?

Остальные строки — в подробном виде. Добавить выбор размера текста. В текущем Pine таблица фиксированная `2 × 9`, `size.small`.

Для старой таблицы H5 сохранять смысл отдельных показателей, а не объединять разные условия в один голос «покупать/продавать». Неприменимую строку Эллиотта `BTC-only` скрывать на золоте и ES. Актуальность исходного скриншота проверить перед изменением старого индикатора: это другой скрипт, не новая таблица `bot7 · режим сеток`.

### 3.3. Срок, источник и полнота снимка

Передавать раздельно:

- время сборки строки;
- возраст/время источников, насколько это можно достоверно определить;
- число прочитанных и ожидаемых живых сеток, список/причины пропусков;
- выпуск прогноза и конец его окна действия;
- источник котировки/режима, символ и таймфрейм.

Сейчас `u` — время сборки, `skipped` не попадает в `tv_line`, а `day_corridor` не сохраняет границы действительности прогноза для Pine. Свежая строка может быть неполной. В Pine старый коридор продолжает отображаться после истечения его окна; одного окрашивания возраста через 12 часов недостаточно.

При неполных данных не делать вид, что прочитаны все сетки. При просроченном коридоре убрать его статус «действующий», скрыть или явно пометить устаревшие линии. Предупреждение должно сохраняться и при нуле успешно прочитанных сеток: в `level_lines` текущий вывод `skipped` находится за условием `g['grids']`.

### 3.4. Средняя и настоящий безубыток

`avg = cost / qty` — средняя цена входов, а не безубыток после комиссий: [tv_levels.py:79](https://github.com/alexey-chechikov/chat-bot-v2/blob/1d303fcbd76b9ff8bc2a73b48c5a4f48a7d5a8ac/services/tv_levels.py#L79). Pine и `level_lines` называют её «безубыток лотов».

Переименовать в **«средняя открытых лотов, без комиссий»** либо отдельно рассчитать безубыток с явно указанными учитываемыми комиссиями и, если применимо, финансированием. Не смешивать её с биржевой средней объединённой позиции.

### 3.5. Разрешение режима и работа процесса

Надпись Pine «ЛОНГ — сетки работают» получается из SMA: [Pine:166](https://github.com/alexey-chechikov/chat-bot-v2/blob/1d303fcbd76b9ff8bc2a73b48c5a4f48a7d5a8ac/docs/tv_pine_scripts/bot7_regime_grids.pine#L166). Она не подтверждает доступность процесса, `enabled`, паузу и блокировки входов.

Назвать расчёт **«режим разрешает LONG»**. Фактическую работу показывать отдельно по доступным подтверждённым данным и времени их обновления. При пользовательской смене источника/длины SMA обозначать справочный расчёт, если он больше не соответствует конфигурации ботов.

### 3.6. Дальние линии и ближайшее событие

Текущий `lineMax` ограничивает только `plot` SMA/порога. Импортированные коридор, зоны и средняя рисуются отдельно, без этой отсечки: [Pine:140](https://github.com/alexey-chechikov/chat-bot-v2/blob/1d303fcbd76b9ff8bc2a73b48c5a4f48a7d5a8ac/docs/tv_pine_scripts/bot7_regime_grids.pine#L140).

Применить фильтр дальних линий ко всем подходящим импортированным уровням; значения оставить доступными в подробностях. Добавить расстояние от цены к меткам ближайшего входа/тейка и привязку к сетке. Так дальняя средняя не будет сжимать текущие свечи.

### 3.7. Алерты

Сначала установить фактическое наличие активных оповещений; утверждение Copilot о нуле — его наблюдение, здесь интерфейс независимо не проверен.

Приоритетные события: подтверждённая смена действующего дневного режима; устаревший/неполный снимок; выбранные актуальные уровни бота. `alertcondition` в исходнике сам по себе не создаёт активное пользовательское оповещение. Оповещения об условиях старого снимка/настроек нужно проверять после обновления.

Не переносить пять рыночных цен из ответа Copilot как бессрочные актуальные уровни. Дневной порог меняется; событие закрытия дня должно использовать подтверждённый бар и действующее правило бота.

### 3.8. Карточка сценариев и измерений

Доработать существующую подачу «сценарий → условие → последствия → отмена → оповещение». Для расчёта по лотам явно указать путь цены, ограничения и предпосылки исполнения.

Фразу «по прямой это худший случай для мешка» заменить более точным описанием: **«модель непрерывного снижения до нижнего края при исполнении предусмотренных лимиток»**. Один путь и край статистического коридора не устанавливают гарантированную верхнюю границу потерь.

В рабочем приватном интерфейсе показывать результаты за определённый период: реализованный/нереализованный результат, комиссии, финансирование, максимальную просадку и различие истории, симуляции и живой торговли. Риск счёта оценивать по совместной кривой всех живых стратегий; сумма их отдельных максимальных просадок не заменяет этот расчёт. В публичный Git передавать схему и синтетические примеры; фактические балансы, позиции и частный учёт туда не добавлять.

## 4. Полный текст Copilot: что полезно и что не следует считать установленным

Полезны структура, приоритеты, явные условия, проверка алертов, видимость лотов и вопросы к измерению результата. Достоверность торговых выводов надо оценивать отдельно от убедительности оформления.

### 4.1. Необоснованные выводы о системе

| Утверждение Copilot | Корректная оценка |
|---|---|
| «0 стратегий на графике — систему никто не измерял» | Не установлено: исследования, replay и бэктесты могут работать вне TradingView. Наличие технических тестов отдельно не доказывает доходность. |
| Дубли горизонтальных линий означают фиксированный шаг сетки | Логической связи нет; шаг нужно брать из действующей конфигурации и логики движка. |
| `loading` означает два мёртвых индикатора | Один снимок не устанавливает причину; проверить повторную загрузку, ошибки и фактические значения. |
| Пустая `/tv` означает сломанную интеграцию | При предусмотренном ручном импорте это может означать отсутствие вставленной строки. |
| Весь риск оператора в одном BTC | Не соответствует известному описанию BTC/ETH и пяти сеток; фактическую концентрацию оценивать по учёту. Пять сеток сами по себе также не доказывают диверсификацию. |
| Лонг-сетка набирает максимум лотов у сопротивления | Зависит от алгоритма доборов, тейков и текущего состояния; по видимой цене этого не установить. |

### 4.2. Объём, ADX и ранжирование

- Значение `0.42 × среднего` нельзя уверенно интерпретировать без таймфрейма, определения среднего и статуса свечи. Незавершённый дневной объём может сравниваться с полными прошлыми сутками. Использовать закрытые бары либо сравнение одинаковой части суток; при этом обозначить метод.
- Даже корректно измеренный низкий объём сам по себе не доказывает заявление «пробои систематически проваливаются». Для этого нужна статистика именно заданного условия и результата.
- ADX 18.6 описывает измеренную силу тренда; не доказывает границы указанного диапазона или прибыльность сетки.
- ADX доминации 34.5 сам по себе не показывает направление. BTC.D — доля капитализации, а не непосредственное измерение денежных переводов в BTC.
- Одновременное попадание INJ в momentum и mean-reversion может описывать разные свойства и горизонты. Удаление от EMA200, RSI или противоречие рейтингов сами по себе не доказывают преимущество шорта.
- «3 из 6», «4 из 8» или «5 из 8 бычьих» не являются оценкой вероятности роста; условия могут быть зависимыми.
- R:R полезен для разметки сделки, но без вероятностей, издержек и реализуемости входа не устанавливает ожидаемую доходность.
- Порог R:R 2:1 не является универсальным доказательством пригодности или непригодности сделки. Приведённые Copilot 0.42:1 требуют проверки вероятности, издержек и правил исполнения, а не одного сравнения с 2:1.

### 4.3. Проверенная арифметика по числам текста Copilot

Это проверка приведённых им чисел, а не сегодняшних текущих котировок.

| Пункт | В тексте | Пересчёт |
|---|---:|---:|
| BTC 83 402 к EMA200 72 771 | +9.6% | **+14.61%** |
| BTC 83 402 ниже максимума 87 396 | −4.8% | **−4.57%**; небольшое расхождение может отражать время снимка |
| Снижение 87 396 → 80 684.36 | −8.32% | **−7.68%**; 8.32% — величина обратного роста |
| Стоп 82 267 от входа 82 700 | −0.52% | **−0.524%**, верно |
| T1 84 463 при входе 82 700 / стопе 82 267 | 4.1R | **4.07R**, верно |
| T2 87 396 при тех же входе и стопе | 10.8R | **10.85R**, верно |
| +1R | 83 133 | **83 133**, верно |
| S1 82 648 − 0.5 × ATR(4H) 763 | стоп 82 267 | **82 266.5**, округление верно |

Если подтверждающее бычье закрытие 4H даёт другой фактический вход, R:R и +1R пересчитываются. Стоп 82 267 и структурная инвалидация 81 182 могут описывать разные события, но это нужно подписать явно.

SMA100 74 615 и 74 825 в разных местах ответа требуют указания источника, символа, времени и закрытого/формирующегося дневного бара. Разные расчёты не следует выдавать за один управляющий показатель бота.

### 4.4. Предложение Copilot меняет торговое правило

Закрытие лонгов после **4H ниже 80 684** отличается от действующего правила **дневного закрытия по SMA100** с указанным в снимке порогом около **74 739**. Это новая политика выхода, а не найденная неисправность действующей.

Если рассматривать её, оформить отдельный сравнительный эксперимент на одинаковых данных, с одинаковыми издержками, параметрами сеток и явным разделением обучающего/проверочного периода. Аналогично проверить предложение переставлять центр сетки и начинать новые лонги только из указанной Copilot зоны. Сам разбор не служит подтверждением таких изменений.

Pine-стратегия может быть полезна для визуальной проверки формализованных правил. Её совпадение с многосеточным движком, лимитами, частичными исполнениями и моделью комиссий нужно отдельно проверять. Отсутствие Pine-стратегии не обнуляет существующие внешние исследования.

Прежние отрицательные проверки индикаторов не доказывают автоматически несостоятельность каждого нового конкретного сетапа Copilot. Сами новые сетапы также пока не имеют предъявленной отдельной проверки. Возможен журнал вперёд с заранее записанными условиями входа/отмены, горизонтом, издержками и результатом, без изменения реальной торговли ради проверки.

### 4.5. Новости

Две новостные ссылки, приведённые Copilot, открыть и подтвердить не удалось. Это не доказательство выдумки или ложности новости. До проверки даты и первоисточника не использовать их как установленное обоснование сегодняшнего сценария. Новостной блок должен различать проверенные и непроверенные катализаторы.

## 5. Паспорт системы, который стоит давать Copilot

Перед следующим разбором предоставлять обезличенный структурированный контекст:

- BTC/ETH, пять сеток на WEEX; какие стороны принадлежат ботам и какие оператору;
- источник котировок графика и источник управляющего дневного режима: это могут быть разные биржи/инструменты;
- правило режима, UTC, длина SMA и использование подтверждённых дневок;
- индивидуальные шаги, ограничения логических слотов/позиции и причины блокировки;
- средняя открытых лотов с точным определением; её отличие от биржевой средней;
- ближайшие действующие заявки и тейки, актуальность и полнота снимка;
- факт наличия внешних исследований и схема результатов без частных аккаунтных сумм;
- требование разделять факты, вычисления, гипотезы и недостающие данные.

Так Copilot сможет анализировать вашу систему, а не реконструировать её по одному открытому графику.

## 6. Рекомендуемая последовательность следующего прохода Claude

1. Подтвердить или опровергнуть F1–F4 на искусственных данных и добавить проверки поведения, отличающегося от текущих тестов. Для каждого пункта дать результат и версию кода. Подтвердить падение новой проверки на исходном дефекте в изолированном worktree, а не из-за изменения интерфейса. Новые каталоги включить в `scripts/_run_tests.py`; после исправлений выполнить полный штатный прогон.
2. Отдельно воспроизвести F5 с контролируемым worker и реальным механизмом замка в подходящей изолированной среде. Не запускать тест, который может поднять рабочие службы.
3. Сопоставить сценарий и движок на одном снимке: цены по тику, число логических слотов, остаток входа, потолки, комиссии и причины остановки доборов.
4. Улучшить контракт снимка: полнота, пропуски, действительность прогноза и явно определённая средняя. Не скрывать неполные данные за текущим временем сборки.
5. Доработать краткую/подробную таблицу, ближайшее событие, фильтр дальних линий и подписи фактического состояния. Проверить на разных таймфреймах и на неполном/просроченном вводе.
6. Проверить настоящие активные алерты в интерфейсе оператора; не считать наличие кода подтверждением подписки.
7. Результаты измерений показывать отдельно от операционной исправности. Новые торговые идеи Copilot оформить как проверяемые варианты с заранее определёнными правилами.

### Минимальная матрица приёмки

| Проверка | Ожидаемый результат |
|---|---|
| Стоимостной потолок достигнут раньше слотов | Сценарий останавливает следующие входы и показывает причину |
| Один `parent`, несколько partial fills | Число слотов совпадает с движком; объём остатка не удвоен |
| Граница коридора между сырой ценой и округлённым тиком | Число достигнутых ордеров совпадает с движком |
| Одна сетка с повреждённым числовым полем | Остальные видны; снимок неполный, причина пропуска показана |
| Все сетки не прочитаны | Явная ошибка покрытия, без подмены нулевыми лотами |
| Время строки свежее, окно прогноза истекло | Коридор не обозначается действующим |
| Изменён источник/период SMA | Справочный расчёт не называется подтверждённым режимом ботов |
| Средняя входа показана | Подпись не обещает безубыток после комиссий |
| Дальний импортированный уровень | Фильтр применяется; значение остаётся доступным в подробностях |
| Stop при заблокированном fake `tick` | Вторая копия не получает право работать до окончания первой |
| Неполный текущий дневной объём | Метод сравнения явно указан; нет вывода о дефиците объёма по несопоставимым периодам |

В ответе Claude перечислить исправленные/опровергнутые пункты, новые проверки и итоговый SHA. Результаты живой сверки и любые изменения процесса описывать отдельно от результатов изолированных тестов.

Следовать существующему разделу «Цикл с GPT» в `CLAUDE.md`: перед приёмом передачи проверить, что diff содержит только `docs/`, использовать fast-forward и не запускать чужие воспроизведения на машине с живыми ключами. Торговые изменения готовить и согласовывать по действующим правилам репозитория. Для новых стратегических гипотез сохраняется его протокол измерений и ворот, без обязательного долгого paper-периода.

## 7. Оставшиеся вопросы исходного отчёта

- Золото в исходном отчёте обозначено как `dry_run`; интерфейс должен явно отличать симуляцию от живых сеток. Этот разбор не устанавливает его доходность и не является решением включить/выключить торговлю.
- Сравнение «четыре против одной», отчёт задержек исполнения/тейка/пополнения и запись стакана остаются отдельными задачами исходного отчёта; текущая передача не подтверждает их выполнение.
