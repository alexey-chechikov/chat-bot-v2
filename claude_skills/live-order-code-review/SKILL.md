# Живой ордерный код — чек-лист
Источники: разборы GPT 10–12.10 — R1–R7 (`docs/WEEX_GPT_STATE_RECHECK_2026-10-11.md`), L1–L8
(`docs/WEEX_LIVE_REGIME_REVIEW_ANSWERS_2026-10-12.md`), разбор 11.10 (`docs/WEEX_GPT_STATE_REVIEW_ANSWERS_2026-10-11.md`).
Команды — абсолютными путями: `/Users/alexeychechikov/code/bot7/.venv/bin/python3 /Users/alexeychechikov/code/bot7/<путь>`,
git — `git -C /Users/alexeychechikov/code/bot7`; без `cd` и `$(…)`.

## Инварианты
1. **Намерение на диск ДО отправки** (`pending` / `flatten` с cid, qty, srv-время); ACK и привязка id к владельцу —
   одной атомарной записью (R1).
2. **Неизвестный исход ≠ конечный.** `{}`, HTTP-ошибка, нет статуса, чужой orderId, неполная история → владение
   сохраняется, повторной отправки нет. Конечный — только статус из TERMINAL при совпавшем orderId (`Grid._detail`,
   L4). Пустая история — не доказательство «не дошёл» (L2, R2); искать и по `user_trades` окна → деталь → clientOrderId.
3. **Новый market — только после конечного статуса прежнего и учёта его исполнений** (L2). Отказ POST и конечный
   исход без исполнения — оба в счётчик повторов; ACK его не обнуляет (L5).
4. **Один реестр владельца** с курсором по orderId для КАЖДОГО ордера бота: вход, тейк, stray, рыночное закрытие,
   стоп. Иначе `_orphans` усыновит свой же market (L1), а `_settle_fees` удалит курсор живого ордера (L7).
5. **Частичные исполнения:** накопительный курсор `filled/filled_val`, прирост учитывается ровно один раз; остаток
   живёт под защитой; эпизод закрывается только при подтверждённом нуле (разбор 11.10, п.9).
6. **Учёт сохраняется ДО записи в журнал** (L8).
7. **Общий потолок:** «занято» = лоты + стоящие входы + неясные постановки + сироты-входы; нечитаемый учёт →
   свободно 0; место пересчитывать перед каждой сеткой/монетой; усыновлённая сирота сразу занимает место (R5).
8. **Передача стороны оператору** — сначала довести отправленное (вход, тейки, market), потом «передано» по
   фактическому остатку (L3).
9. **Режим/внешние данные:** решение привязано к дате, данные валидированы; битые → «неизвестно» (новых входов
   нет, нового закрытия нет; начатое доводится) (L6).
10. **Битый конфиг/учёт → GridHalt**, никогда не значения по умолчанию другой монеты.
11. Биржа не различает владельца одинаковых контрактов одной стороны (ручной LONG оператора + LONG бота) —
    reduceOnly закрывает объём стороны.
12. **Ручные позиции и ордера оператора неприкосновенны.** Свои — только по префиксу `b7g`/`b7t` (`self.open`
    фильтруется по PREFIX). Сторона из `release_sides` (BTC SHORT) — ни одного ордера бота: ни входа, ни снятия, ни
    reduceOnly. Рыночное закрытие по режиму — строго на сумму лотов бота, не на позицию биржи.
13. **CRLF:** в репо ~600 файлов с CRLF (общие с Win), не только `app_runner.py` и `services/telegram_runtime.py`.
    Перед правкой — `git -C … ls-files --eol <путь>`; `w/crlf` → только Edit или байтовый скрипт
    (`read_bytes`/`write_bytes`); после — `git -C … diff --stat`: число строк не должно удвоиться.

## Тесты
- Базовые `DryExchange` / `DryTrendExchange` НЕ умеют часть сценариев: `open_orders` не отдаёт PARTIALLY_FILLED,
  `order_info` всегда полный, у тренда `place_market` не отказывает reduceOnly без позиции. Нужен подкласс по образцу
  `PartialLiveExchange` (`tests/services/weex_grid/test_weex_regime_gpt.py:23`): PARTIALLY_FILLED в open_orders,
  пустой/ошибочный ответ детали, отказ reduceOnly без позиции, задержанное исполнение, потерянный ответ после
  исполнения. У грид-имитатора `place_market` reduceOnly без позиции отказывает.
- Каждый дефект — тест, который ПАДАЕТ на старом коммите и проходит на новом (рецепт — `model-answer-comparison`,
  «тест на старом коммите»); падение — на дефекте, а не на смене интерфейса. Новый защитный тест — проверить
  мутацией (подменить код на поломку — тест обязан упасть).
- Обязательные регрессии: `tests/services/weex_grid/test_weex_release.py` (передача стороны;
  `test_manual_short_untouched_by_regime_close` — ручной шорт и ручной тейк оператора переживают закрытие лонгов по
  режиму, неизвестный режим и возврат режима; ловит 3 мутации), `test_weex_regime_gpt.py`, `test_weex_regime.py`,
  `test_weex_review5.py`, `test_weex_grid_review2..4.py`, `test_weex_portfolio.py`.

## Деплой (живые деньги)
Пока хоть одна сетка или тренд ведётся живьём (`dry_run=false`, сейчас BTC и ETH; входной ордер стоит и при 0 лотов),
ЛЮБОЙ kickstart — и любой автоперезапуск launchd (KeepAlive=true, 14 стартов за 10–12.10) — грузит всё рабочее
дерево. Торговый код = `services/weex_grid|weex_trend|weex_api`, `app_runner.py` (запуск weex-задач), обработчик
`/weex` в `services/telegram_runtime.py`.
0. Правку торгового кода, которая ждёт «да» оператора, готовить в worktree (`git -C … worktree add
   <scratchpad>/fix HEAD`), в живое дерево переносить после «да» — не оставлять неодобренное в живом дереве.
1. `scripts/_run_tests.py` — всё зелёное.
2. Перед ЛЮБЫМ kickstart: `git -C … status --short -- services/weex_grid services/weex_trend services/weex_api
   app_runner.py services/telegram_runtime.py` — пусто или только одобренное оператором. Есть правка торгового
   кода без «да» → показать `git -C … diff --stat` и дифф логики, ждать «да» (исключение из памяти
   `feedback_deploy_after_fix`). Остальной код при чистом торговом — kickstart сразу, без вопроса.
3. Копии учёта в scratchpad с меткой времени: `state/weex_grid_state.json`, `state/weex_grid_eth_state.json`,
   `state/weex_trend_*state*.json`. Копии — только для разбора: откат — только кода через git; учёт из копии без
   оператора не восстанавливать (движок примет новые ордера за сирот и забудет лоты после копии).
4. `launchctl kickstart -k gui/501/com.bot7.app-runner`.
5. `research/weex/account_now.py` — оба учёта обновлены (цикл жив), переданная сторона цела →
   `research/weex/orphan_check.py` — сирот 0 и лотов без тейка 0 (находка сразу после постановки — перепроверить
   через 10–20 с) → `research/weex/pnl_reconcile.py BTC` и `… ETH` — ИТОГ «совпадает» →
   `research/weex/errors_today.py <дата>` — нет новых ERROR и WARNING о деньгах.
